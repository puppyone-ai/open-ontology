## Purpose, input and boundary

Current executor.rs binds an unnamed portal, sends Execute limit0, Close and Sync before reading all results. This is unsuitable for pull-driven bounded batches. Implement a named-portal primitive to consume one bounded Execute response completely before the next Execute. Initial execution uses one row per Execute to make byte-budget behavior demonstrable; faster row windows require separate equivalent semantics proof. Never declare suspension merely because downstream byte budget is reached. Caller receives one row or a terminal state only after the appropriate protocol transition is understood; it never silently discards pending rows.

Inputs: exclusively borrowed admitted PgConnection inside an already established read-only owner transaction; internal authenticated SELECT/mapping and bound values; positive row-window allowance and pre-reserved source rate grant; R2-W receive limits installed before any source response. Output: owned typed row plus explicit suspended/complete/error state and bounded diagnostics. Do not expose arbitrary SQL or raw connection through Open Ontology public APIs. Driver may need ordinary internal SQLx primitives; connector public boundary must remain admitted catalog only. Complete-result row count and per-Execute row count are distinct. A server CommandComplete after the final row is not a full snapshot Finished token; multi-table owner determines full-run success.

Proposed interface and path set MUST be frozen by coordinator before coding. Candidate locations are vendored PG connection executor, a dedicated portal module and connection/lib reexports as necessary, a new finite-wire Rust test and a real-PG portal test, vendor PATCH.md and versioned portal contract. Core buffered meter/stream/error/manifests/locks/snapshot/session/types are read-only unless explicit handoff. Integration into snapshot owner/Arrow streaming belongs R2-S. R2-P must not reach into the live a125 schema guard writer's files. If safe API lifetime/argument metadata requires extra paths, first deliver exact proposal; do not improvise shared-path edits.

## Required state machine

Track bounded unique portal and statement identifiers per connection without unbounded retained cache; explicitly handle counter exhaustion. Prepare/Describe/Bind confirmations and parameter metadata must be fully consumed. No runtime schema discovery may bypass the source budget or wire limits. Parse/Bind/Execute/Flush/Sync ordering, pending ReadyForQuery count and transaction status must be correct on real PostgreSQL, not assumed from a fake peer.

Execute allowance must be positive, never implicit unlimited0; reserve rate allowance BEFORE sending it and document control/failed/retry accounting. Flush lets the server return responses without ending the portal lifecycle. Consume all responses for the current Execute until PortalSuspended, CommandComplete, EmptyQueryResponse or ErrorResponse. Notices/ParameterStatus retain bounded R2-W handling. No next Execute while prior response remains unread. No early Sync that discards protocol state. A row cannot be duplicated on resume or skipped on a byte boundary. Unexpected tag, excess row, malformed metadata, bad transaction status or mismatched completion poisons the connection with a masked typed outcome.

At suspension retain the same named portal and same transaction/cut. At normal exhaustion close owned portal/statement as appropriate, observe CloseComplete and correct Sync/ReadyForQuery accounting, leaving the owner transaction alive until the owner rolls it back. Handle ErrorResponse recovery according to actual extended protocol: consume required synchronization or hard-close; never reuse a connection whose readiness is uncertain. Cancellation at send/flush/receive/row-return/suspend/close/sync must retain enough state for an explicitly safe resume or poison/hard-close. Borrowed future drop must not silently permit another query on a dirty connection. Explicit close is bounded; asynchronous Drop cannot claim confirmed backend cleanup. R3/owner integration must later prove backend release <=5s; no unrelated termination and no COMMIT or source writes here.
