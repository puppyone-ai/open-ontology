## 我们要交付的产品

Open Ontology交付一套产出Ontology的系统。企业给出数据库或文件信息，系统接入获准数据，自动构建语义草案，供人审核、修订和发布。用户取得标准YAML、审核overlay、Git版本、Knowledge Pack及经Gateway访问数据的接口，可以接入自己的harness。

CLI、HTTP/SDK、MCP或后续接入形式提供同一套Ontology与数据访问能力，核心产物的使用不要求启动内置Pi。内置Pi用于让用户立即试问，也作为内部验证客户端；它要做好，但不是产品的最终形态。源库密码与查询方言留在接入端。

数据库类型的扩展是现在最先要做的事。当前交付闭环优先；后续独立任务在固定依赖、文件边界和资源条件满足时并行开发，产品版本按顺序签收。正式审核、发布和完整Plan中尚未验收的功能按后续闭环有序交付。按当前 docs 来源 revision 4、OO-SPEC-001 和 OO-PLAN-001 做完整产品，范围包含 SP00至SP15 和 DBX。

## 按五次真实产品交付推进

执行顺序以[产品交付闭环台账](PRODUCT-LOOPS.md)为准，必须先读它，再领取当前范围的工程卡。五次交付是累计可用版本，分别为：至少十种数据库的Ontology预览产品、可审核发布的Ontology产品、通用外接服务、持续更新的企业工作台、完整发行产品。

当前是DL01：实际支持至少十种独立数据库产品，MySQL和Oracle不可缺；每种走输入连接、只读复制、本地构建和实际消费的整条流程，不能只交连接器。默认十源名单、版本冻结和验收要求在该台账中。早期版的预览与实验限制明确保留，不能称生产认证。

五版按DL01至DL05顺序签收，开发按真实依赖安排。当前DL优先；后续版任务在依赖实现和接口已提交并固定SHA、文件范围独占、资源有余量且不挤占当前关键路径时，可以由协调者明确派发。缺实例、许可或人工签字只阻塞相关验收，不阻塞无关公共功能。后续任务完成不等于后续整版签收，也不自动切换当前DL。已存在代码和证据先核对复用。SP和DL共同描述同一套实现：任务及证据共用，每个父项/阶段注明在哪一版全部签收；一个组件或Pi六问不能完成整版。DL05必须同时完成全部必交SP和完整Plan，只有原明确后续扩展不在本轮。

各能力首次交付即验证正确性、只读、必要权限、取消和恢复；具备条件的目标尽早启动nightly，客户题目和授权准备同步推进。最后一版负责汇总与补齐，不把验证全部留到最后。

每个闭环按台账勾选条件交出固定制品、可用说明、真实旅程、独立复审和证据，回归上一版能力。最多五次，均在整体Goal的范围和安全要求内；最后DL05及整体目标全部适用退出条件通过后才结束。

## 数据库接入做到什么程度才结束

对一个声明支持的数据库，用户输入连接信息后，系统应能检查它能读什么、按什么方式读，把数据正确搬到独立的本地库，并说明读取限制。随后这些数据要能用于构建 Ontology 和真实问答。读取失败时要说明原因，取消后要停下来，整个过程不能写源库。

先做好共用接入接口、驱动隔离、数据转换和变更读取，再逐个数据库验证。DBX-W01至W05负责这些基础能力，W06至W13负责各类数据库，DBX-W14负责逐目标测试、版本回归和证据检查；支持等级还要经过对应的测试和审阅。所有源都通过 Arrow 汇聚到本地 PostgreSQL Agent DB。

同一个库的不同产品、版本、部署方式、驱动和能力分别验收。例如，一个版本能批量导入，不能据此宣称它的增量读取也通过。没有实例、许可证或云账户时，写明缺什么条件，继续做其他能完成的工作。

精确退出条件：按 Spec 7A 和数据库准入文档区分 experimental、verified、certified。verified 所需的连续14天 nightly 等条件保留；certified 还要满足客户和发行条件。尚未实现的命令不供用户当作可用功能。没有对应证据的目标保持原等级。

## 自动构建和发布做到什么程度才结束

数据库搬到本地后，系统能读出表结构和数据画像，调用真实 Builder 模型，生成可供人审核的 Ontology 草案。相同输入可以复用缓存；模型失败时留下失败记录，不产生可审核或可发布的假成功。成本拿不到时要明确说明。

用户能看懂并审核草案，审核结果真正影响后续内容。系统把标准 YAML 和审核 overlay 保存到 Git，形成可追踪的版本，完成发布，再编译出 Agent 实际使用的 Pack。

精确退出条件：Self-build S0至S10 在真实控制面连续证明各阶段的状态、失败、重试、缓存、成本、审核和分类。S10是分类，发布在后面另验。标准 YAML、overlay、Git版本、发布和Pack之间必须用同一条真实流程证明，分段工具测试只能完成各自的子任务。当前PG未审核草案的成功记录保留其限定范围。

## 外部harness接入做到什么程度才结束

外部调用方能取得已发布Pack或读取同一版本的Knowledge，用已实现的CLI、HTTP/SDK、MCP等接口理解数据库和查询本地数据。客户端、模型或harness可以更换，Ontology格式、版本和Gateway契约保持一致，查询仍受对应用户和角色的权限约束。

验证时使用非内置Pi的真实调用方，不由内置Pi替它执行工具。核对产物版本、字段含义、查询结果、权限拒绝、取消和审计；每个声明可用的接入形态完成对应测试。外部调用方不需要OO启动Pi或维持内置对话会话。需要注册或撤销的访问状态按对应协议验证，不与内置聊天的会话状态混用。

面向任意harness意味着产物和接口开放、可适配，实际验证过哪些客户端、协议和版本要照实声明。CLI/HTTP/SDK先按SP09交付，MCP按SP13完成；不能将尚未实现的形式标为可用，也不能以只在Pi中成功代替外接验收。

## 内置Pi做到什么程度才结束

Pi读取刚生成的Pack，自己写SQL，经CLI/Gateway查本地数据，答案对独立预期结果，并能取消、关闭和重开。它提供“接入后马上能问”的体验，帮助发现构建和接口问题。已有十万行物流PG六问保留为这条内部回归，源断开后再试问，保留原类型并对typed oracle。

新增数据库仍需自己的真实构建与消费用例。内置Pi验证和外部接口验证分别记录，二者都按各自范围验收，不把演示通过写成整个Ontology系统已交付。
