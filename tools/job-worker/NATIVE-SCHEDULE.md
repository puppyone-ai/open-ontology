# Native capture scheduler operator contract

## 2026-10-13 recovery successor

For current native scheduling, install jobs 0000–0004 with `crates/oo-jobs/tools/deploy.py`, then install the exact `jobs-claim-selected/1` migration on the **control** DB with the pinned Loader's `install-native-claim-selected` command. `native-install` adds the worker tables; it does not install base jobs or create historical ACKs. The worker checks the 0009 checksum before claiming. C4 may use a separate operator-pinned target DB; other methods currently use the configured control DB as target.

`native-step` chooses the oldest immutable pending occurrence per `(source_id,target_database)` and calls real `jobs.claim_selected` for that UUID. For queued C1 requests, the sealed per-table generation orders generation 2 before 3 even if retry `run_at` changed. Existing queued tasks without `source_progress` gain only their active task fence after a real claim. C1 baseline comes from that binding's successful control watermark and matching sealed target table/run/apply receipts; the global target source watermark is checked as a position barrier, never used as the table generation. A failed claim or target import does not advance either watermark.

`native-cancel --project UUID --task UUID --worker OWNER --generation N` accepts an exact active C4 task, or a C5 task only while queued at the exact generation with no pending ACK; the fixed worker retains the same verified target-watermark and active-fence checks. It calls published `jobs.cancel` only when no pending ACK or target sidecar exists and the target source watermark still equals the verified control ACK chain. For a task already terminal `failed` or `cancelled`, `native-fire`/`native-step` perform the same target checks before clearing only its active fence. The old task, request, attempts, and audit remain. C4 requests that omitted `mirror` are invoked with `mirror:false` while their stored source request remains unchanged; an explicit `mirror:true` is rejected.

Use `crates/oo-jobs/tools/deploy.py --container OWN_CONTROL --database DB --loader-role INTERNAL_LOGIN` to install the checksum-checked base jobs functions on a fresh control DB. Install the Loader's target migrations separately on the approved target. Credentials stay in private files.

Build `cargo build --locked --manifest-path tools/job-worker/Cargo.toml` with Rust1.94 Linux. CLI takes `--config PRIVATE_CONFIG` with host,port,database,runtime_user,runtime_password_file,admin_user,admin_password_file,migrations; TCP additionally requires ca_file and verified TLS. An absolute Unix socket host permits local socket transport without ca_file. No TCP TLS bypass exists. Password files are existing private hex tokens; no token in arguments.

1. `native-install`: install worker-owned `jw_native` tables using operator admin.
2. `native-put --manifest PRIVATE_OR_OPERATOR_MANIFEST`: register/update enabled schedule; no enqueue yet.
3. `native-fire --project UUID`: atomically enqueue due occurrences through real jobs.enqueue, store immutable manifest, and schedule next DB-time period. A queued/running occurrence prevents overlap for that binding.
4. `native-step --project UUID --worker OWNER`: real jobs.claim_selected, producer invocation, durable producer request, loader invocation with actual lease_id/generation, 10s heartbeats, real complete_success CAS + worker watermark in one transaction (C4 target ACK follows CAS).
5. `native-serve --project UUID --worker OWNER --seconds N`: continuously fires and claims using the preceding operations. Stop process to stop execution; queue is durable; next owner recovers after published30s lease expiry.
6. `native-enable --binding UUID --enabled true|false`: pause/resume future occurrences. Inflight claims remain authoritative; source DBA window must wait until running tasks have completed.

Manifest schema (unknown fields refused):

```json
{"protocol":"oo.jobs.native-schedule/v1","binding":"UUID","project_id":"UUID","source_id":"actual_source_id","method":"C5","cycle":"pull","period_ms":6000,"producer":{"path":"/absolute/source-owned-producer","sha256":"actual64hex","args":[]},"loader":{"path":"/absolute/pinned-oo-pipeline","sha256":"actual64hex","args":["import-native-update"]}}
```

`method` is C1/C2/C3/C4/C5; `cycle` is detect/pull/reconcile. Each cycle/table binding has its own period. Method is a declaration, never capability proof. Source owner provides the actual adapter, semantics and admission evidence. Executable script hashes are supported; scripts must use a pinned/declared interpreter in their runtime. Source secrets are never in job payload. Producer fixed argv is operator configuration, never job-supplied argv. Producer stdout must contain only actual `oo.pipeline.native-update/v1` request; diagnostics go stderr. Producer stdin:

```json
{"protocol":"oo.jobs.native-producer/v1","binding":"UUID","pin":1,"source_id":"actual_source_id","method":"C5","cycle":"pull","period_ms":6000}
```

Producer must run the real source driver and existing admission sealer, including source-owned original witness. It supplies proper source_generation/parent, nonzero/valid applied position codec, snapshot, full typed Arrow, correct source/table identities and target.database matching worker DB. It must NOT perform target imports itself, call jobs.claim, write trust receipts itself, or fabricate lease fields. Worker inserts only canonical `{v,binding,pin}` payload in jobs.tasks; it never generates admission receipts or certificates. Occurrence stores source-produced request before target import so lease-loss/restart reuses exactly that request, then supplies new real lease id/generation. Loader independently verifies source admission and locks that task via jobs.loader_hold before target effects.

Success requires authoritative verify_inputs trust, actual matching locked lease id/generation/owner, source_bound, loader_invoked and committed control mirror (or replay). Receipt booleans alone cannot establish claim: worker additionally completes through actual published CAS in target DB. Native target atomicity and effective watermark are loader responsibilities. Worker watermark advances only in same transaction as successful CAS and never overwrites a later pin. Period changes keep inflight occurrence manifest immutable; they apply to future occurrences. A failed/refused source/loader never writes the watermark and uses server-governed retry. Target commit/control mirror recovery uses the saved request on re-claim and loader replay; no second source capture for that occurrence.

All source DBA mutation windows require explicit pause + no active occurrence first. Claims/watermarks inspection is real SQL on jobs.tasks/jw_native.occurrences/jw_native.watermarks. This contract is executable functionality; source acceptance still requires independent full typed cells comparison, update/delete/replay, configured periods, and old-owner/restart evidence.

The manifest may additionally include operator-owned registration:

```json
{"registration":{"admission_binary":"/absolute/pinned-source-admission","admission_sha256":"actual64hex","registry_path":"/absolute/source-owned/{binding}/{pin}/registry.json"}}
```

Registry path placeholders are substituted ONLY from the immutable occurrence binding UUID/pin, never arbitrary task text or producer output. Producer publishes real sealed registry bytes at that operator-approved path before returning its request (and durably dedupes the same binding/pin). Worker validates admission executable SHA, reads registry bytes, computes their integrity SHA, and passes only `OO_NATIVE_ADMISSION_BIN`, `OO_NATIVE_BINDING_REGISTRY`, `OO_NATIVE_BINDING_REGISTRY_SHA256` to Loader. That hash establishes byte integrity; actual pinned admission tool and Loader `verify_inputs` establish source/witness/catalog trust. The worker does not manufacture any receipt, registry, witness or admitted bit.

Manifest C1/C2/C3/C4/C5 map exactly to NativeUpdate runtime `capture_method` tokens c1_cdc/c2_change_feed/c3_cursor/c4_partition/c5_diff; a different producer method is refused. Multiple table bindings may share one actual project/source/cycle; UUIDbinding is unique, source identities must never be faked to bypass table scheduling. Producer must persist exact captured request keyed by binding+pin before stdout so a crash before worker response persistence returns the same request on retry.

The retained Linux ELF requires the pinned Rust1.94 build/runtime image (`docker.io/library/rust@sha256:0f24958fa693fe838859faf64a0ec78d382cd543a6b6efd0fa7a3bcb10ea90d5`). Direct copying into older PostgreSQL images can fail GLIBC2.38/2.39 dependency checks. Use the pinned Rust runtime on the owned target network with caller-CA verified TLS, or mount the owned local PostgreSQL socket into that runtime. Do not mount a Docker socket. Source producer owns and isolates its existing driver/runtime-library/secret requirements.

`native-state --binding UUID` is a read-only resume API. JSON `oo.jobs.native-state/v1` returns schedule settings and `applied=false` when no successful occurrence exists. Once target import/mirror and published completion CAS succeed together, it returns matched `pin`, `task_id`, `lease_generation`, `source_generation`, `applied_pos`, `load_state`, `advanced_at`, `position_codec`, `position_lineage`, and optional `sqlserver_candidate_position` from that exact succeeded occurrence request. A merely produced/captured, running, retried or target-mirror-pending candidate is never returned as applied. C1/C2 producers must select next prior position from this acknowledged state, while retaining binding/pin dedupe for pending capture requests.

Producer stdin additionally supplies nullable `acknowledged_source_generation` and `acknowledged_pin`, read from the preceding real `jw_native.watermarks` CAS-success transaction. These values are null before the first worker-acknowledged import. Producers must choose generation from this actual acknowledgment (or separately verified initial target baseline), never simply from pin after a terminal failed occurrence. Same binding/pin still returns the exact durable candidate. A target commit whose job completion did not succeed remains pending; use saved-request Loader recovery, and explicitly stop for operator recovery if the server attempt cap is exhausted. Failed attempts never create a successful acknowledgment.

After rerunning `native-install`, every completed producer/loader subprocess keeps its original bounded stdout/stderr bytes and exit code in private `jw_native.process_attempts`, keyed by actual task/generation/stage and executable SHA. This includes unsuccessful child exit and valid Loader JSON whose decision is refused. PUBLIC has no privileges; only internal jobs runtime/operator may inspect. Worker console prints lengths/exit/stage only, never raw source values or secrets. Limits are 4MiB stdout and 64KiB stderr (one extra byte detects overflow, then refuses); overflow diagnostics are bounded rather than claimed as a complete unlimited stream. For a real loader failure, the operator may inspect `SELECT exit_code,convert_from(stdout,'UTF8'),convert_from(stderr,'UTF8') FROM jw_native.process_attempts WHERE task_id=... AND stage='loader'` privately. Review before exporting logs to Git; customer values/secrets remain private.

`native-loader-put --manifest OPERATOR_MANIFEST` explicitly approves a patched Loader executable and admission registration for an existing binding. The manifest binding/project/source/method/cycle must match the server binding. It stores a separate operator override, approved DB principal/time/SHA; it NEVER modifies original occurrence manifest or saved source request. Future steps validate both original immutable occurrence hash and current operator override hash, use only override loader/registration (the original producer/captured input stays pinned), and record both identities. This permits recovery with a genuinely repaired fixed Loader without executing an obsolete pinned Loader or rewriting task rows. Run `native-install` to install the override table before use. Do not approve source/table/target changes through this loader operation.

For C1/C2/C3/C5, the worker clones the saved request for invocation and forces `mirror:true`; the stored source request stays byte-equivalent/immutable. Loader owner verified `mirror` is an invocation-only policy excluded from native payload/source-admission identity. For an existing committed native batch, corrected Loader validates the same actual source admission and live claim, returns replay without a second COPY, and performs actual `_oo.native_update_mirror` before the worker can complete through CAS. C4 uses `mirror:false` and the separate post-CAS target ACK. Console records the invocation overlay and process receipt retains actual output; no manual watermark, certificate, source hash or stored request rewrite is permitted.

NativeUpdate's replay result deliberately has `loader_invoked:false` to mean no COPY was repeated. A real replay may complete only when the pinned Loader process actually ran, `verify_inputs` trust/source binding are valid, its locked lease receipt exactly matches the current claimed task/owner/generation, and actual mirror status is inserted/replay; published jobs CAS must still succeed. `loader_invoked:false` on awaiting_publish or any unfenced/untrusted result remains refused.

For continuously captured C1 T groups, the operator may set `transaction_registry_vector_path` to an absolute path containing both `{binding}` and `{pin}` and omit `transaction_registry_vector_sha256`. Only those two placeholders are accepted; this mode is unavailable to S1 baseline imports. Static paths still require the exact SHA. The pinned producer seals and durably publishes the vector at that fixed operator path before returning. The worker substitutes only the immutable occurrence identity, bounds and hashes the actual bytes, and retains the first observed vector in private `jw_native.process_attempts` under `stage=registry_vector`. Every recovery attempt of the same UUID must match those bytes exactly before Loader invocation. This stage is a worker observation, not a child process result or admission decision. Producer output cannot select a path. The Loader still independently checks all registry digests, complete transaction scope and authoritative admission seals. Source capture/slot ACK remain source-owner responsibilities; this registration does not advance a source slot.
