# Private source onboarding recipe

`python3 tools/source-onboarding/onboard.py --input /absolute/private/input.json [--resume]`

Input protocol `oo.source-onboarding/v1`: `connection` has exactly `type`, `database`, `host`, `port`, `user`, `secret_ref`; `secret_registry`, `recipe`, `out` are absolute paths. Input, recipe, template, registry and resolved secret must be caller-owned regular files with no group/other permissions. Inline passwords/tokens are refused. The registry maps exact SecretRefs to private files; secret contents are never read by this runner. Output directory is new and private. Resume requires identical input, recipe, program pins and completed artifacts.

Recipe protocol `oo.source-onboarding.recipe/v1`: `engine`, `owned_fixture: true`, `config_template`, `connection_map`, `pins`, `steps`. Engine is one of postgresql/mysql/oracle/mariadb/sqlserver/clickhouse/doris/starrocks/mongodb/opensearch. Customer full import is not authorized. Customer recipes must use `mode: metadata_sample`, `read_only: true`, and `max_rows` 1..5; their fixed source-owner driver enforces metadata/LIMIT5 and zero source writes. Owned fixture recipes use `mode: whole_source` (default). A receipt must retain which mode actually ran.

`connection_map` maps existing JSON pointers in the template to `host`, `port`, `database`, `user`, `secret_ref`, or `password_file` (resolved path). All five actual connection fields including password_file must be consumed. Template retains authorized tables, types, source semantics, budgets, periodic schedules, target and operator identity. A recipe may not substitute a fixture connection for these fields.

`pins` is a list of absolute `path`/`sha256` program and script identities. Each step has a unique `name`, `argv` (no shell expansion; only `{config}` and `{run}` substitution), `deadline_seconds`, and nonempty `artifacts` of relative `path` and optional expected `sha256`. Executables must be pinned. Interpreted scripts and other dependencies must also be pinned by the source owner. Docker wrapper executables and container image/binary identity checks belong in the fixed source-owner wrapper. All outputs used to claim the new run must be created under `{run}`; historical evidence can be a declared immutable dependency but cannot be its fresh result.

Source owners retain authority for real permission/type preflight, admission/Loader/CAS/ACK ordering, capture method C1–C5, periodic insert/update/delete/recovery, model input equivalence, S0–S10 authenticated decisions, Ontology/Pack maintenance and Gateway/CLI/dialogue oracles. This runner never invents any of those receipts. Complete-chain recipes must return a fresh manifest covering those exits with actual current source/generation and referenced artifact hashes. Old failures and paid model records remain unchanged. An immutable reviewed model can only be reused through the existing semantic/fingerprint verifier; a new semantic input needs the genuine model path.

Raw stdout/stderr are private files, not printed. Each attempted stage is journaled before spawn; failure remains in the journal. Resume skips only verified completed stages. Interrupted running stages require the source-owner operation's existing idempotency/recovery rules. The runner does not roll back databases. `recipe_completed` means the declared recipe exited zero and artifacts were retained; it is not product acceptance, publication or customer signoff.

Current status: orchestration implemented; actual ten-source complete-chain recipes and fresh real runs are being supplied by source owners. Missing SQLServer native amd64/EULA/TLS/authorized endpoint remains a hard gate, with no automatic EULA acceptance.

`mode: source_capture` explicitly labels an owned-fixture capture/admission-only recipe. Whole-source mode describes the intended recipe scope, never acceptance. Capture-only source owners should use source_capture; actual complete-source status still requires the fresh final product manifest and independent root verification.

User entry: an owner-only JSON containing just the six connection fields is accepted by the same `onboard.py --input CONNECTION`. The locally installed engine registry selects the fixed source-owned recipe and secret registry, creates a fresh private durable run, and remembers its pointer for `--resume`. Operators install each actually complete recipe with `register_engine.py --engine TYPE --recipe RECIPE --secret-registry REGISTRY`; these are installation steps, not user-written workflow configuration. Installed recipe hashes are checked. No incomplete capture recipe can be registered.

A whole recipe is registered only with `register_engine.py --engine TYPE --recipe RECIPE --secret-registry REGISTRY --whole-run RUN`. `RUN` must be a private directory whose journal is `recipe_completed` for that exact recipe. The runner accepts whole only when this run's journal shows direct steps launching pinned `product_flow.py` and `tools/agent-product-verifier/dialogue.py`, and their artifacts bind all of the following: `source_fresh` with the catalog bytes' sha256, real S5 (`validated`, builder spawned, not a structural draft, approved model, input sha256), standard OOS (`effective.json` protocol `oo.builder.effective-oos/v1` plus `oos/ontology.yaml`, `oos/effective-oos.yaml`, `oos/source.json`), and the official dialogue verdict (`outcome: verified`, at least two turns, tools `query`/`freshness`/`describe`/`knowledge_cat`, query IDs present in the sibling `transcript.json`, low effort, audit and truth sha256). A boolean `full_product_chain_complete` without those artifacts is refused. `metadata_sample` and `source_capture` cannot register or exit as whole; a capture receipt that sets the whole flag is `capture_cannot_claim_whole`. Source-specific typed oracle, zero-write and recovery evidence stays manifest-bound for root acceptance. These checks do not promote support grade or sign the product. Copying a historical completion into the run is not a direct step.

An optional `approved_tables` list (1..50 entries) can accompany the six plain connection fields or appear beside the wrapped `connection`. A source-owner recipe exposing `approved_tables_pointer` routes this selection into the existing driver's template; unknown support is refused. The existing driver validates selected schemas/tables/columns against actual grants and type/capture capability before reads. Selecting a table never authorizes source DML, schema changes or higher read budgets.

Source-write authorization is connection-specific. An owned-fixture recipe's configured host/port/database/user must already equal the supplied connection before mapping. Changing one of those fields refuses before child spawn; an operator cannot redirect fixture mutation stages at a customer endpoint. A customer connection must use the bounded read_only metadata_sample recipe. Adding another owned fixture requires source-owner installation of its actually authorized template, not a caller-controlled owned flag.

An installed engine may also expose `--metadata-recipe METADATA_RECIPE`. The ordinary six-field entry automatically selects this bounded read-only path when its connection differs from the authorized owned-fixture template; without a bounded path it refuses before any child. A metadata-only engine can be installed before its whole chain is ready, but reports only metadata_sample and never whole support. Capture-only recipes remain unregistrable.
