# Lite foundation -- partial S2-A-02 delivery

This is **not yet the seven-service healthy stack**. `oo up` starts Agent DB,
control DB and model-egress; returns `foundations_only`, `healthy: false`, exit 1.
The individual foundation services can be healthy without product acceptance.
Worker/scheduler bindings, control migrations, Agent DB loading and a reviewed
Pack/Gateway operator directory still need integration. Nothing is auto-reviewed
or published. The `integration` compose profile describes existing executables,
not idle stand-ins; its operator configurations are not generated by this card.

## Build and run

From this checkout, build one platform at a time (both are the default):

```sh
python3 deploy/lite/build_images.py --run-id my-lite-build
cargo build -p oo-cli --locked
./target/debug/oo up --config stack.yaml --json
./target/debug/oo status --config stack.yaml --json
./target/debug/oo down --config stack.yaml --json
```

The build script writes the native image's immutable content ID beside `oo` as
`oo-lite-image`. An installed CLI needs that same companion file and image.
`OO_LITE_RUNTIME_IMAGE` can explicitly override it, but must be a digest, not a
tag. Images are local repository builds, never pushed. Base image indexes and
PostgreSQL are digest-pinned; both Linux architectures use the same Dockerfile.
Builds are serial and refuse to start with less than 8 GiB of host space free.
Builder and helper locks reuse existing dependency versions; root Cargo.lock is
unchanged. The first draft path is described in [DRAFT.md](DRAFT.md).

`model.base_url` also accepts `{"secret_ref":"model-endpoint"}`. The endpoint
stays a reference in normalized configuration; model-egress reads and validates
the private file at use time. Lite copies it with the same ownership, permission
and explicit-rotation rules as the model key.

The S2c native arm64 image includes `oo-load`; the image build checks its
`--help` entrypoint. This is packaging, not source-to-draft integration.
The retained amd64 lock is historical and does not include this change.

First up creates a private `.oo/lite/pki` CA, component mTLS certificates and
random admin password via `oo_stack::credentials::bootstrap`. Repeated up never
rotates credentials. Source/model references are copied into the deployment's
private home; changed credentials require explicit rotation, not replacement.
Under D14, lite PostgreSQL accepts TCP only with TLS and a SCRAM password;
clients must still verify the server certificate and hostname. Database client
certificates are optional. Standard and Gateway/internal mTLS are unchanged.
No database port, Docker socket or host network is exposed. Model-egress listens
only on its container loopback. This is a single-owner boundary, not multitenant
isolation. Oracle client runtime installation is not included.

Every compose container, network and volume has `oo.lane=a`; project names are
scoped to the canonical state directory. Lifecycle checks ownership before
acting. A non-overlapping private subnet is selected without deleting existing
networks, including when Docker's automatic address pools are exhausted.
`down` stops only this compose project and retains its database volumes and
credentials. The acceptance runner separately removes only its own labelled
fixture volumes after teardown. No prune or unrelated-container cleanup occurs.

## Status and pending integration

Status exposes actual compose service states. Job success/failure timestamps
come from `jobs.task_events` and next due from enabled `jobs.schedules`, filtered
by the project in `work/operator/schedule.json`. It uses one read-only snapshot
as `oo_jobs_runtime` over the owned control container's local socket. It never
uses local build receipts, dispatch exit codes, or a computed polling deadline
as evidence of completed work. Missing configuration is `not_configured`;
missing schema, database errors or malformed results are `unavailable`, with
null timestamps rather than stale fallback data. Down does not query the DB.
With a deployment-local `health-client.json` containing
`token` and `ca` filenames under `pki/`, it calls the configured HTTPS Gateway's
`/v1/health` using a private bearer file and verified CA. The minimum of the
API's token/certificate deadlines is reported; arbitrary response fields are
not relayed. Without an enrolled credential/Gateway it says `unmeasured`, not
healthy. Local bootstrap certificate expiry is a separate measurement.

Card S2d authorizes a separate internal health/meta-only operator token on first
up; the user's first token remains S4. The current implementation does not yet
issue that operator token. In addition to operator setup, the shared
token-store and job-worker TCP clients currently use `with_no_client_auth()`,
which cannot connect to lite's `clientcert=verify-ca` database. This is not
resolved by the Builder-only TLS fix. No TLS exception is installed here.
The opt-in scheduler invokes the existing `job-worker native-fire` operation.
It needs installed control schemas, worker configuration and a project UUID in
`work/operator/schedule.json`. Gateway needs its existing reviewed operator
directory. The builder remains a one-shot unreviewed metadata draft, not an
Agent DB loader. These prerequisites are why full S2-A-02 is still **not done**.
Additionally, `oo-load` publishes views in `oo_load_data`, while the Builder's
existing PostgreSQL catalog selects physical tables only. Builder profiling uses
TLS without a client certificate, while lite's database requires mTLS. A direct
connection switch is therefore insufficient; no TLS exception or invented
catalog is installed by this delivery.

## Evidence

- `a-s2d-control-live-2`: PostgreSQL 17.10, real control migrations and
  fixture-driven scheduled no-op success/failure transitions; measured DB
  timestamps, missing-schema failure, empty DB and project/disabled-schedule
  filtering. This does not test the production scheduler or seven services.
- `a-s2d-control`: lifecycle regressions, workspace check and CLI/stack tests.
  Failed live attempt 1 is retained (fixture used a non-allowlisted error kind).
- `a-s2d-operator-boundary-1`: the real `issue-token install` exits 1 against
  the production lite PostgreSQL TLS policy. The server records
  `connection requires a valid client certificate`; a CA-verified connection
  presenting the fixture client certificate succeeds against that same DB.
  Reproduce with `cargo build -p oo-gateway --bin issue-token --locked`, then
  `python3 deploy/lite/test_operator_boundary.py --run-id <new-run-id>`.
  That result describes the pre-D14 policy. The current regression instead
  requires TLS/SCRAM token issuance to succeed and rejects plaintext,
  a mismatched server hostname and an untrusted CA.
  Both fixture runners remove their own containers and secrets.
  Worker client-auth remains a source-inspected limitation, not a live worker
  test. Authenticated `/v1/meta` also delegates to published-data freshness;
  a pre-publication health/meta-only operator contract needs lane B integration.
- `a-s2c-endpoint`: endpoint-reference parsing/egress/lifecycle regressions,
  workspace check, CLI/stack tests and source-boundary inspection.
- `a-s2c-runtime`: native arm64 runtime build and real `oo-load --help` launch.
- `a-s2c-foundations`: three healthy foundation services with an endpoint
  reference, idempotent credentials, truthful partial status and owned cleanup.
  No paid model calls, three-engine drafts or seven-service acceptance occurred.
- `a-s2b-mysql-2`: four requested MySQL versions; synthetic model replay.
- `a-s2b-pty-5`: real PTY save/equivalence, completion, failed execution,
  explicit retry, status and q cancellation; secret scans pass.
- `a-s2b-live-draft-final`: one-table PostgreSQL 17.10 metadata draft through real
  gpt-6.1-sol model-egress, unreviewed/unpublished, no Agent DB load.
- `a-s2b-foundations-final`: three healthy foundation services, idempotent bootstrap,
  truthful partial status and teardown; NOT a healthy seven-service stack.
- `a-s2b-images-protoc`: both architectures built, six executable launch checks;
  immutable IDs in `images.lock.json`, detailed evidence in `s2b-evidence.json`.
- Prior-card evidence remains in `evidence-summary.json` and CLI evidence files.
