# Lite deployment

An unconfigured `oo up` starts Agent DB,
control DB and model-egress; returns `foundations_only`, `healthy: false`, exit 1.
The individual foundation services can be healthy without product acceptance.
Worker/scheduler bindings, control migrations, Builder service lifecycle and
the Gateway operator directory still need integration. Nothing is auto-reviewed
or published. The `integration` compose profile describes existing executables,
not idle stand-ins; its operator configurations are not generated by this card.
An explicitly configured retained scheduler can now complete the seven-service
loop. See [RETAINED.md](RETAINED.md) for its owner-reviewed input contract and
the distinction between scheduled acceptance and automatic first-up onboarding.
Under D16, an `oo up` from the CLI also provisions the retained build chain
(status `retained_ready`, exit 0) and `oo build` runs every stage inside this
runtime image; see `crates/oo-cli/src/admin/RETAINED-BUILD.md`.

## Build and run

From this checkout, build one platform at a time (both are the default):

```sh
python3 deploy/lite/build_images.py --run-id my-lite-build
cargo build -p oo-cli --locked
./target/debug/oo up --config stack.yaml --json
./target/debug/oo status --config stack.yaml --json
./target/debug/oo down --config stack.yaml --json
```

The build script writes the native image's immutable content ID beside `oo` as
`oo-lite-image`. An installed CLI needs that same companion file and image.
`OO_LITE_RUNTIME_IMAGE` can explicitly override it, but must be a digest, not a
tag. Images are local repository builds, never pushed. Base image indexes and
PostgreSQL are digest-pinned; both Linux architectures use the same Dockerfile.
Builds are serial and refuse to start with less than 8 GiB of host space free.
Builder and helper locks reuse existing dependency versions; root Cargo.lock is
unchanged. The first draft path is described in [DRAFT.md](DRAFT.md).

`model.base_url` also accepts `{"secret_ref":"model-endpoint"}`. The endpoint
stays a reference in normalized configuration; model-egress reads and validates
the private file at use time. Lite copies it with the same ownership, permission
and explicit-rotation rules as the model key.

The S2c native arm64 image includes `oo-load`; the image build checks its
`--help` entrypoint. This is packaging, not source-to-draft integration.
The retained amd64 lock is historical and does not include this change.

First up creates a private `.oo/lite/pki` CA, component mTLS certificates and
random admin password via `oo_stack::credentials::bootstrap`. Repeated up never
rotates credentials. Source/model references are copied into the deployment's
private home; changed credentials require explicit rotation, not replacement.
Under D14, lite PostgreSQL accepts TCP only with TLS and a SCRAM password;
clients must still verify the server certificate and hostname. Database client
certificates are optional. Standard and Gateway/internal mTLS are unchanged.
No database port, Docker socket or host network is exposed. Model-egress listens
only on its container loopback. This is a single-owner boundary, not multitenant
isolation. Oracle client runtime installation is not included.

Every compose container, network and volume has `oo.lane=a`; project names are
scoped to the canonical state directory. Lifecycle checks ownership before
acting. A non-overlapping private subnet is selected without deleting existing
networks, including when Docker's automatic address pools are exhausted.
`down` stops only this compose project and retains its database volumes and
credentials. The acceptance runner separately removes only its own labelled
fixture volumes after teardown. No prune or unrelated-container cleanup occurs.

## Status and pending integration

Status exposes actual compose service states. Job success/failure timestamps
are separate from each service row's `Kind`, `Status`, and `Healthy` fields.
Builder is a one-shot `job`: `exited` with a measured zero exit code is
`succeeded`, not a failed daemon. A running Builder has not yet completed.
An exited job with no usable exit code is `unmeasured`. Long-running services
need both `running` and an actual `healthy` healthcheck result; running alone
is not health evidence. A successful Builder row does not imply publication
or make the entire stack healthy.

Job success/failure timestamps
come from `jobs.task_events` and next due from enabled `jobs.schedules`, filtered
by the project in `work/operator/schedule.json`. It uses one read-only snapshot
as `oo_jobs_runtime` over the owned control container's local socket. It never
uses local build receipts, dispatch exit codes, or a computed polling deadline
as evidence of completed work. Missing configuration is `not_configured`;
missing schema, database errors or malformed results are `unavailable`, with
null timestamps rather than stale fallback data. Down does not query the DB.
With a deployment-local `health-client.json` containing
`token` and `ca` filenames under `pki/`, it calls the configured HTTPS Gateway's
`/v1/health` using a private bearer file and verified CA. Optional `cert` and
`key` filenames provide a deployment-local mTLS client identity; both must
be private 0600 files. The minimum of the
API's token/certificate deadlines is reported; arbitrary response fields are
not relayed. Without an enrolled credential/Gateway it says `unmeasured`, not
healthy. Local bootstrap certificate expiry is a separate measurement.

First up issues a separate internal health/meta-only operator token; the user's
first token remains S4. Token-store admin/runtime credentials are distinct from
the database superuser password, stay private, and are reused on repeated up.
Issuance runs in a one-shot bootstrap container, not an eighth steady service.
Changing the operator audience requires explicit migration. D14 resolves the database client-certificate
blocker. The Gateway health/meta-only role contract now passes the S2f live probe.
The opt-in scheduler queues `lite_retained` jobs in the control database.
Its worker runs `oo-load sync`, verifies the retained data-only Builder digest,
publishes through `publish-retained`, measures Gateway reload, and prunes.
It needs installed control schemas and the owner-provisioned configuration in
`work/operator/schedule.json`. Gateway needs a deployment-local operator
directory, but no publication is required for the restricted operator role.
Builder remains a one-shot job, not a healthy daemon. These prerequisites are
not automatically installed by the foundation-only `oo up`.
Builder now supports `oo_load_data` views. `oo build --agent-target` explicitly
loads the source and hands its verified view receipts to that catalog path.
This does not install the native worker's legacy admission/watermark state,
nor does it make the opt-in Builder a long-running healthy service.

## Evidence

- `a-s2f-pg-draft-3`, `a-s2f-mysql-draft-1`, `a-s2f-oracle-draft-2`:
  `oo build --agent-target` loads an owned fixture into a separate Agent DB
  and produces an unreviewed draft from its real published views. Versions:
  PostgreSQL 17.10, MySQL 8.4.11, Oracle 23.5.0.24.07. Each uses one live
  generation call through private-file model configuration. This is not a
  Gateway publication or a seven-service/scheduled-cycle pass.
  Failed PostgreSQL fixture attempts (non-clean session startup) and Oracle
  attempt 1 (missing CURRENT_SCN read privilege) remain in evidence.
- `a-s2f-boundary/integration-seams.json` records source-inspected wiring gaps.
  The former `serve` worker accepted `pg_effect` in its proof project, while
  `native-fire` creates `native_capture`. The opt-in worker now invokes
  `native-step` for the same configured project as the scheduler; dispatch
  success still does not imply task completion. The native no-change path
  checks durable parent admission in `jw_native`, not `oo-load` receipts in
  `_oo_load`. No parent watermark or successful task was invented to bridge
  these contracts. This inspection is not a live scheduled-cycle test.
- `a-s2f-first-up`: real first `oo up` issues the reserved operator token through
  the runtime image; repeated up preserves its bytes and credentials. The three
  foundation services are healthy. Gateway is still unavailable, so the overall

  The runner removes its containers, volumes, network and private credentials.
