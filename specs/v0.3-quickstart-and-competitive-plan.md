## 0. 背景与结论

竞品分析的判断“OO 主要是设计”已经过时。v0.2 已在 PG 13–18、MySQL 5.7–9.5、Oracle 11g–23ai 跑通全链：快照/CDC、Self-build、审核、发布、Gateway、Agent 读数，有固定证据。但它的核心论断仍然成立：**对 PoC 用户，Auto-Ontology 用 6 步、几分钟就能看到答案，OO 是天级。**

用户从零到 Agent 第一个答案，现在要过这些关（均有文件依据）：

| # | 卡点 | 依据 |
|---|---|---|
| 1 | npm 0.2.0 未发布（`ETARGET`），GHCR 运行镜像私有（403） | `README.md:320`，ledger E432，TODO S6-B-01 |
| 2 | 没有示例库：必须自带带 TLS 的 PG/MySQL/Oracle、只读账号、CA PEM，并逐个列出 `schema.table` | `docs/guide/quickstart.md:8-34`；`wizard.rs:355-371` |

**目标**：一个只装了 Docker 和 Node 的陌生人，**3 条命令、5 分钟内、不需要模型 key、不需要自己的数据库**，就能让 Agent 读到第一个可审计的答案。同一次体验里还要亲眼看到 OO 的差异化：行列权限拒绝、审计记录、新鲜度、版本。之后用户再换成自己的库，才走现在的完整流程，那时只是“换一个 source”，而不是从头学起。

## 0.5 本轮范围与产品形态（2026-11-08 owner 定）

范围：P0（快速体验）、P1（接入自己的库）、P2 第 1–3 项（预检工具、MCP 工具面、A/B 评测）。Ossie、skills、远程 OAuth 往后放。

### 产品逻辑（一句话）

输入数据库信息 → 选表 → 产出 ontology → 看图确认 → 产出 Agent 可用的 MCP / CLI，以及装进 CLI profile 的 Gateway token。多个数据库对应多个 profile。

### 用户触达压缩成一条命令、五个界面

`oo init` 是唯一入口。`oo quickstart` 等于 `oo init --demo`。所有界面都有非 TTY 等价参数，`--json` 输出同样的产物。

| 界面 | 用户做什么 | 系统做什么 | 依据/复用 |
|---|---|---|---|
| ① 连接 | 粘贴连接串或逐项填写；或选“没有数据库？用示例库” | 识别引擎，跑只读 doctor：账号权限、TLS、CDC 能力。每项打绿勾或给出修复指引 | `doctor.rs`、`wizard.rs` |
| ② 选表 | 空格勾选；`a` 接受推荐；`/` 搜索 | 只读目录元数据，不读数据行，给每张表打 ✓推荐 / ?待定 / ✗不推荐，并附一句理由 | 见下方“推荐规则” |
| ③ 构建 | 等待（显示阶段与预计时间） | 拉数、画像、模型起草本体、编译 | `oo build` 链路 |
| ④ 图谱确认 | 在 ASCII 知识图谱里浏览实体和关系；处理 ⚠ 项；按 `Enter` 确认发布 | 图谱视图 / 关系文字列表 / 实体详情三个 Tab，⚠ 面板列出需要人看的项 | 现有 ratatui 审核屏 `review.rs` |
| ⑤ 交付 | 默认直接拿到：已登录的 CLI profile + 一段可复制的 share prompt；可选再生成 MCP 配置 | token 自动写入 CLI profile（`oo profile <名>`）；打印 share prompt，并支持一键复制；`m` 键生成 Claude Code / Cursor / Codex 的 MCP 配置；最后跑一次 `oo check`（readiness）给出绿灯 | `packages/cli` 已有 `--profile`、`share-prompt` |

交付默认走 **CLI + prompt**（owner 已定），MCP 是可选项。

**选表推荐规则**（owner 已定：规则 + 元数据，不调模型，表名不出本机）：
- 不推荐：名称像日志、临时、备份或框架表，例如 `*_log`、`*_tmp`、`*_bak`、`*_old`、`*_history`、`audit*`、`queue*`、`session*`、`flyway_*`、`django_*`、`schema_migrations`；空表；分区子表；没有主键也没有唯一键的表。
- 推荐：被外键引用多的表（实体中心）、码表（小表且被引用）、名称像业务对象的表。
- 待定：其余。
- 理由都写在行尾，例如“被 6 张表引用”“名称疑似日志表”。用户的选择记进 stack.yaml，保存时展开成显式清单。

**ASCII 知识图谱**：
- 实体是方框，方框内写实体名、主键和行数量级。关系用线连接，标注基数（`1─<`）。
- 布局：分层布局，外键中心实体放中间。超过约 25 个实体时，默认改成“焦点实体 + 一跳邻居”视图，用方向键在实体之间跳转。
- `t` 切换到文字关系列表（如 `订单 >─1 客户 via orders.customer_id`）。
- 非 TTY 下可以导出：`oo ontology graph --format ascii|text|mermaid`。

**确认规则（D28，owner 已定）**：
- 用户只做一次显式的“确认发布”，确认绑定图谱摘要 hash。
- ⚠ 项不交给用户兜底，也不一律从严。产品用自己的数据分析和 pipeline 能力**按证据裁决**：数据证据强就采用，证据弱才不采用。每条裁决都附上证据和分数，图谱里可以看，用户可以推翻。
- 原则是“错误代价不对称”：
  - 敏感数据错放出去不可逆，所以从严。
  - 关系、指标、实体错过一条，Agent 就答不出或答错，代价同样真实，所以不能为了安全一律丢弃。
  - 每类都用离线金标（T6 与 OO-Logistics）调阈值，并同时看 precision 和 recall。

| ⚠ 类别 | 产品用的证据 | 采用条件（默认，可按金标调） | 不采用时 |
|---|---|---|---|
| 关系（无声明外键） | 包含度：子列非空值落在父键中的比例，全量或大样本计算；类型与长度兼容；父列唯一性；命名相似度；视图定义与查询日志里的 JOIN 共现；由数据实测的基数 | 包含度 ≥ 0.98 且父列唯一，或者包含度 ≥ 0.9 且有命名或 JOIN 证据。基数按实测值写入，不靠猜 | 图谱里画成虚线，标出缺少哪项证据（如“包含度 0.71”） |
| 敏感或个人信息列 | 列名规则；取值画像：格式命中率（手机、证件、邮箱、银行卡）、基数、熵；表的语境 | 命中率 ≥ 阈值则标为 `personal/sensitive` 并隐藏。只因名称可疑但取值画像否定时，判为非敏感，避免误伤普通列 | 正常可见 |
| 指标（模型起草的 SQL） | 在副本上执行对账：结果非空，单位与列语义一致，不跨重复键聚合，和逐行重算的结果一致，跨时间窗口稳定 | 通过全部对账检查就采用 | 降级为“示例查询”，不作为认证指标 |
| 实体主键 / 展示名 | 唯一性实测（全量去重率）、非空率、是否被引用、取值是否可读 | 去重率 = 1 且非空，就当作主键；展示名取可读性最高的唯一或近唯一文本列 | 退成普通数据集 |
| 码表与码值 | 小表且被引用；码值覆盖率（事实表的取值落在码表中的比例） | 覆盖率 ≥ 0.99 时认证为完整码表 | 标为“不完整”，依赖它的指标降级 |

**这一步取代现有的逐条审核屏。** 要改的点：`review.rs` 的“每项必须有显式 decision”改成“确认 + 默认裁决记录”；`decisions.yaml` 记下每条默认裁决与来源规则，审计可追溯；REVIEW.md 与 G 门禁的相应条款随之修订。

**Profile 与多库**：
- 每个数据库一个 profile（gateway 地址、token、CA）。`oo use <profile>` 切换。
- MCP 服务按 profile 启动，Agent 配置里写的是 profile 名，不写凭证。
- 再接一个库就是再跑一次 `oo init --profile 新名`。

## 1. P0：快速体验（`oo quickstart`）

### 1.1 用户视角（验收形态）

```bash
npm install -g @reduxxx888/ontology-cli
oo quickstart            # 拉镜像、起示例库与 lite 栈、装好已审核的 demo 本体、发布、签发本机 token
oo try                   # 跑 3 个示例问题 + 1 个被拒的问题，打印 SQL、结果、freshness、审计 id
```

结束时打印两样东西：一段可直接粘贴的 Agent 配置（Claude Code / Cursor / Codex 的 MCP 配置或 share prompt），以及一句 `oo quickstart --down` 的清理提示。

### 1.2 设计要点

| 项 | 做法 | 复用 |
|---|---|---|
| 示例库 | `demo` compose profile 里加一个 PG 容器，灌入公开安全的合成数据：OO-Logistics 子集，8–12 张表、含码表与日历，几万行。不用 WWI，避免许可与体积问题 | `bench/datagen/`、`deploy/logistics-demo/pg/seed.sh`、`testing/engines/gold`（T6 已有 12 表 20 题金标） |
| TLS / 账号 | 本机生成一次性 CA 与只读账号，标记 `local_fixture`；不放宽生产默认（D14） | `deploy/lite` operator-bootstrap |
| 免模型 | 随包发布 demo 的 **已审核** 本体与 Pack（curated、带 hash），`quickstart` 直接 publish，跳过 Self-build 与审核。用户提供模型 key 时，可加 `--rebuild` 现场演示自动生成和审核队列 | `oo ontology export/open`、publish 链路、`build_retained.rs --resume` |
| 镜像 | 依赖 GHCR 公开与 npm 发布（owner 决策，见 §5 D25）。另需多架构（linux-x64/arm64、macOS），并测镜像体积对首答时间的影响 | `lite-images.yml`、`cli-binaries.yml` |
| 权限演示 | demo 自带两个角色（analyst、ops），各配一条行过滤和一条列禁止；`oo try` 里有 1 题被拒，并显示审计记录 | Gateway 角色 / `roles.yaml`、审计表 |
| `oo try` | 只读：调 Gateway 的 `query`，打印 SQL、行、`freshness`、`audit_id`、`published_generation`。不是 server 端问答，SQL 来自 demo 金标；明确告诉用户“真实使用时由你的 Agent 写 SQL” | T6 金标 SQL、`oo query`、`oo freshness` |
| 非 TTY | `oo quickstart --yes --json` 全程不交互，CI 也能跑 | 现有 `--json` 约定 |
| Agent 接入 | 把 MCP 桥随 npm 包发布（预编译二进制或 Node 实现），`oo mcp-config --agent claude|cursor|codex` 输出配置；本机场景不需要搬 CA 文件 | `tools/mcp-gateway`、`oo share-prompt` |

## 3. P2：对标补齐（按竞品分析 §5 的优先级落地）

| # | 项 | 现状 | 做法 | 验收 |
|---|---|---|---|---|

- **P2-T** 预检正负例集；MCP 工具契约；A/B 报告可复现（固定 seed 与模型）；Ossie 往返与有损报告。
- **回归** T0–T8 矩阵在 v0.3 收尾时按 v0.2 的方式重跑并固定证据。

## 7. 风险

- 镜像体积可能让首答时间超过 5 分钟，需要量体积、分层，或给 demo 一个精简 profile。
- 预检工具误拒会伤害体验，必须带评测上线，可先做成 advisory（只提示不拦截）。
- demo 本体随包发布后，要防止被当成“免审核”的先例：用户自己的库仍然走审核，文档要写清楚。
