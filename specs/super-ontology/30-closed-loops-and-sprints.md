# Super Ontology 闭环、Sprint 与验收

> 前提：[00 总纲与决策记录](00-overview-and-decisions.md)。任务卡的细节在 [10 后端](10-backend.md)（`B-S<n>-*`）和 [20 前端](20-frontend.md)（`F-S<n>-*`）。本文只定义每个闭环交付什么、怎么验收，以及前后端在哪里会合。

## 1. 节奏与规则

- **4 个里程碑，8 个闭环，15 个 Sprint**（L6 含 S10b）。 每个里程碑两个闭环；一个闭环包含 1–3 个 Sprint；一个 Sprint 默认 1 周（L3、L4 各有一个 Sprint 是 1.5 周）。
- **每个闭环都是一次完整的功能验收。** 闭环结束时，必须能从用户的角度端到端演示一件新的事，并且通过本文列出的全部验收项。只完成后端或只完成前端，都不算闭环完成。
- **闭环是签收的门，不是开工的门。** 按 70 分册，下一个闭环的代码靠夹具和 mock 提前开写，但签收前不合入集成主线；OO 侧签收后视情况合入 `master`；Puppyone 侧开发期间不碰 `main`/`qubits`，最后集中提一个 PR（D43）。
- **并行与排期见 [70 分册](70-parallel-workstreams.md)**；**形式化验证见 [80 分册](80-formal-verification.md)**，每个闭环签收前对应的形式化门禁必须全绿。
- **提交与签收的追溯规则见 [50 分册](50-commit-and-traceability.md)**：一卡一枝、每个提交带 `Plan:`、签收时打 `super-ontology/L<n>` 标签。
- **端到端测试与 owner 验收见 [60 分册](60-e2e-and-owner-acceptance.md)**：每个闭环签收前 T1、T2 全绿；L4、L6、L8 结束时交付 owner 验收包（打包好的 App）。
- **签收要看证据，不看报告。** 每个闭环都要有一份 `testing/super-ontology/evidence/L<n>/` 目录：演示录屏或截图、各项检查的命令与输出、评测报告、已知问题清单。数字要能在 CI 或证据文件里复核。
- **全绿才合并。** OO 侧的 `aggregate`、`oo-test-fast-l1-l2` 以及本文新增的门禁全部为绿；Puppyone 侧合入 `codex/super-drive` 之前 `test`、`test:typecheck`、`check:boundaries` 全部为绿。不能为了变绿放宽门禁。
- **flag 保护。** M3 结束前，`superDrive` 在 Puppyone 默认关；OO 侧文档流水线只在显式登记 Drive 后才运行，不影响现有数据库用户。

## 2. 总览

| 里程碑 | 闭环 | Sprint | 用户能做到的新事情（演示脚本） |
|---|---|---|---|
| **M0 基线** | **L1** 规格与评测基线 | S1 | 工程师能在两个仓库里打开 flag 看到空壳；评测脚本对合成文档集给出基线分数 |
| | **L2** 行走骨架 | S2 | 在 Desktop 里指定一个装满 Markdown 的文件夹，看到文件和状态；一条命令把它挂进任务目录，打开 `.context/BRIEF.md` 能看到带出处的内容 |
| **M1 第一版** | **L3** 读懂文件 | S3、S4 | 拖进 PDF、Word、Excel、PPT，看着它们走完处理状态；失败的能批量重试；点开文件能看到解析出的块和锚点；本地文件夹和 S3 桶都能增量同步 |
| | **L4** 本体与共享 | S5、S6 | 系统读懂“人、项目、决定、别名”；低置信的进待确认队列，能按来源整体接受；在分享面板里把一个文件夹共享给 Agent，任务目录里出现只含范围内内容的 BRIEF；能撤销 |
| **M2 回流、多模态与演进** | **L5** Suggest 回流 | S7、S8 | Agent 在 `suggest/` 写建议或调 MCP 工具；Desktop 修订模式里批量接受，下一次 BRIEF 就变了 |
| | **L6** 多模态与演进 | S9、S10、S10b | 扫描件、图片、会议录音、录屏都能被读懂，出处精确到页、区域、时间段和说话人；系统提议新类型，人确认升格；刷新时看到差异；`puppyone share` 可用 |
| **M3 规模与扩展** | **L7** 企业与云 | S11、S12 | 只读接入企业的 OSS/COS/R2 桶；Cloud 模式下远端 Worker 也能挂载 |
| | **L8** 规模与轻量 | S13、S14 | 不装 Docker 也能用；1 万文件的 Drive 流畅；语义相近的内容也能被选进 BRIEF |

## 3. 闭环详述

每个闭环按同一个结构写：目标 → Sprint 划分 → 后端交付 → 前端交付 → 会合点 → 验收项 → 不在本闭环。

---

### L1 规格与评测基线（M0，S1，1 周）

**目标**：所有人对“做完是什么样”有可执行的定义。

**S1 交付**
- 后端：
  - `specs/super-ontology/` 五个分册定稿。
  - `testing/super-ontology/golden/`：约 50 份合成中文团队文档 + `labels/`（实体、关系、别名、取代、每条带锚点）+ 1 份红队文件（`redteam/` 子目录，内容含若干唯一的“金丝雀”字符串）。
  - 评测工具 `oo-eval docs`（或 `tools/super-ontology-eval/`）：读标注，算核心类型的精确率、召回率、出处覆盖率、红队命中数，输出 JSON + Markdown 报告。
  - crate 与模块骨架、Cargo feature `docs`（默认关），CI 能编译。
  - 50 分册 §10 的 trailer 检查与台账一致性检查脚本，挂进 CI；`execution/super-ontology/ledger.md` 建好。
- 前端：
  - 从本地 `main` 拉出 `codex/super-drive`（D36、D43：不碰 `main`/`qubits`）；`superDrive` flag 与空 surface 注册；`super-ontology` 主进程服务与 IPC 骨架（返回固定的“未连接”状态）；i18n namespace 建好。
  - Puppyone 仓库放一份指针文档，指向本 spec。

**会合点**：控制 API 的 JSON Schema（10 分册）冻结为 `v1-draft`，前端按它生成类型和 mock。

**验收**
1. 两个仓库在 flag 关闭时，现有测试全部为绿，且行为与基线无差异。
2. `oo-eval docs` 能对评测集跑出一份报告（分数可以是 0），报告格式固定。
3. 打开 flag，Desktop 侧栏出现“Super Drive”，页面显示“引擎未连接”空态。
4. 评测集与 spec 通过私有词表检查（0 命中）。

**不在本闭环**：任何真实的解析与抽取。

### L2 行走骨架（M0，S2，1 周）

**目标**：用最笨的实现，把“文件 → Index → BRIEF → 挂载 → 界面”整条链路打通，后面的闭环只是逐段换成真实现。

**S2 交付**
- 后端：
  - `objectstore` provider 的 `fs` 后端（只读、列举、指纹、BLAKE3）；`DocumentSource` trait。
  - 只支持 MD 与 TXT 的解析器（Rust 内），产出 `oo.doc-ir/v1`。
  - 确定性规则抽取：目录约定（`People/`、`Projects/`）、frontmatter、标题结构。
  - 自动发布 → `oo.context-pack/v1` 最小编译（BRIEF 固定章节 + SHARE.json + manifest）→ `oo context mount`。
  - `oo serve`：`health`、`drives`、`files`、`events`（SSE）；PG 迁移第一批。
- 前端：
  - 主进程引擎管理：Docker preflight、启动 `oo serve`（由它拉起文档引擎容器）、读 token、健康检查。
  - 没打开项目时的“打开 Super Drive”入口（D33，F-S2-11）；Windows 构建强制关闭 flag。
  - 登记一个本地 Drive；文件列表显示状态（只到 `published`）；SSE → IPC 实时更新。

**会合点**：真实 `oo serve` 替换 mock；前端集成测试改为对真引擎跑一条冒烟路径。

**验收**
1. 演示：Desktop 里登记一个含 20 个 Markdown 的文件夹，60 秒内全部显示 `published`。
2. `oo context mount --scope Projects/a --to /tmp/t1` 产出 `.context/`，BRIEF 每一行都有 `[src:…]`。
3. 同一输入两次 mount，`.context/` 逐字节相同（排除 SHARE.json 中的 share id 与时间字段，这两个字段单独校验）。
4. 关掉 `oo serve`，Desktop 显示“引擎已断开”并自动重连；重连后用 `since` 游标补齐期间的事件，不丢状态。
5. 修改一个 Markdown，30 秒内状态重新走一遍，BRIEF 内容随之变化。

6. 顶栏新鲜度指示在 `up_to_date`、`processing`、`publishing` 之间正确切换，显示本体版本（D48 基础版）。
7. Super Drive 底部常驻“数据在本地”说明（D79），默认状态下抓包证明除 loopback 外无出网。

**不在本闭环**：二进制格式、LLM、待确认队列、Share 生命周期。

### L3 读懂文件（M1，S3 + S4，2.5 周）

**目标**：第一版承诺的格式都能被稳定、可解释地解析；每个文件的命运都看得见。

**S3（1.5 周）—— 解析与状态机**
- 后端：parser sidecar（Docling）镜像与 HTTP 契约、沙箱（无网络、只读挂载、资源限额）；calamine 的 Excel 解析与表头、表格区域检测；DOCX、PPTX、电子版 PDF、CSV 的 IR 适配；完整状态机（含 `unsupported`、`too_large`、`encrypted`、`parse_failed` 退避、`extract_partial`、`duplicate`）；作业表 + lease/heartbeat；毒丸隔离；sidecar 崩溃重启。
- 前端：上传（拖拽、多选、文件夹）、上传队列面板；状态列与徽标；失败横幅、按状态筛选、批量重试；详情栏的“解析结果”标签页（块列表 + 原文锚点高亮预览）。

**S4（1 周）—— 增量同步与 S3**
- 后端：`s3` 后端（OpenDAL）、凭证经 `secret_ref`、列举对账（代际标记-清扫）、事件去重、删除与取代（D22 的证据撤回部分）、RustFS 集成测试。
- 前端：Drive 登记支持 S3（端点、桶、前缀、凭证引用）；大目录虚拟滚动；`superseded`、`deleted` 的呈现；磁盘与配额显示。

**会合点**：S3 结束时状态机冻结，前端状态矩阵与后端枚举逐项对齐（契约测试）。

**验收**
1. 评测集每种格式的解析成功率 ≥ 98%；失败文件都有可读的错误码和处理建议。
2. 故障注入：解析中杀掉 sidecar、断开 PG、对象存储返回 5xx、文件写到一半——每种情况下其他文件继续处理，受影响文件最终进入正确状态，没有卡死的作业。
3. 毒丸：一个让解析器崩溃的构造文件，最多重试 3 次后隔离，队列吞吐不受影响。
4. 幂等：同一内容复制成 10 个文件名，只解析一次（`duplicate`）。
5. fs 与 s3 两个后端各跑一遍“新增 → 修改 → 重命名 → 删除”，状态和证据都正确。
6. 1000 份文件的 Drive，冷启动解析完成 ≤ 30 分钟（本机，不含 LLM）；内存峰值在 10 分册给出的上限内。
7. 前端：每一个文件状态在界面上都有对应呈现（状态矩阵逐项截图）；断线重连不丢状态。

8. **自动感知**：在访达里直接往 Drive 文件夹放文件、改文件、删文件，无需在 App 里操作，状态自动更新（D46）；单文件延迟达到 D49 的目标（md/txt p95 ≤ 5 秒，20 页内 PDF/DOCX ≤ 30 秒，XLSX ≤ 20 秒）。
9. 定向同步不触发全量清扫（D47）；新鲜度七种状态全部可见（D48）。
10. 精确失效（D53 前半）：只改格式的 DOCX 不触发重新抽取，证据迁到新版本。

**不在本闭环**：实体与事实（只到 IR）、Share。

### L4 本体与共享（M1，S5 + S6，2.5 周）

**目标**：第一版的完整价值——读懂人、项目、决定，并把正确的那一片安全地交给 Agent。

**S5（1 周）—— Index**
- 后端：确定性规则扩充（人员表、文档元数据、文件名）；LLM 补抽（受 D15 约束 + 开放候选 `Thing`），块级缓存、调用上限、用量接口；resolve（别名、消歧、合并、重定向）；双时间与取代（规则优先）；待确认队列与阈值自动发布；`orphaned_overlay`。
- 前端：待确认队列页（按种类、按来源分组，批量接受或拒绝、按来源整体接受）；详情栏“实体”标签页；实体详情（事实、证据跳转原文、别名、取代历史）；“未配置模型”横幅与用量显示。

**S6（1.5 周）—— Context Pack 与 Share**
- 后端：Context Pack v1 完整编译（全部章节、三级披露、降精度、已拦截计数）；D26 可见性过滤（编译器单一出口）；红队门禁；Share 的 mount、expire、revoke，`refs/` 短期凭证；`oo context mount` 完整参数与退出码。
- 前端：分享面板（范围选择、角色、预算、有效期、任务描述，生成命令、复制、一键执行）；共享列表与状态；撤销确认（写明“已读内容无法收回”）；详情栏“被哪些 Share 用到”。

**会合点**：S5 结束时实体与审核接口冻结；S6 中段完成“在 Desktop 里共享 → 在终端里看 BRIEF”的联调。

**验收**
1. 评测集核心类型：精确率 ≥ 0.85，召回率 ≥ 0.75（配模型）；不配模型时报告单独列出分数，且不报错。
2. **红队：0 命中。** 红队文件中的任何金丝雀字符串、只在红队文件出现的实体名和别名，都不出现在任何不包含该文件的 Pack 里。这是 CI 门禁。
3. BRIEF 出处覆盖率 100%；每个 `[src:…]` 都能在 Desktop 里点开并定位到原文。
4. 确定性：同一本体版本、同一参数，Pack 逐字节相同。
5. 编译单个 Context Pack 的 p95 < 2 秒（1000 文件的 Drive，预算 800）。
6. 待确认队列：按来源整体接受 100 条 ≤ 1 次操作；接受后对应事实在 5 秒内进入新的本体版本。
7. Share：过期后 `refs/` 凭证失效；撤销后本地挂载目录被删除；两种情况在列表中都正确显示。
8. 端到端演示：理念文档第 4 节场景的第 1–3 步和第 6 步（不含 Suggest）能用评测集跑通。

9. **轻量漂移**（D50）：拖入一个改变已有决定的文件，发布新版本后 5 秒内，引用了旧决定的 Share 标为 `drifted`；点刷新得到新 Share，旧 Share 转 `refreshed`。
10. **合并与取代规则**（D51）：规则确定的合并、取代自动执行并进当日变更摘要；只有 LLM 候选的进待确认；被活跃 Share 使用的旧事实被取代时，待确认队列有一条提示。
11. **持续一致性**（00 §5.6）：
    - 新鲜度令牌：拖入文件后立即共享，包要么覆盖它，要么在 BRIEF 第一行和 `coverage` 写明未覆盖；`--require-complete` 时覆盖不到直接失败（D54）。
    - 包内一致：包发出后除 `UPDATES.md` 外字节不变（`pack_digest` 校验）；任务内带 Share 凭证的查询读 Share 版本（D61）。
    - 变更必达与提交前闸门：被用到的决定被撤回后，几秒内 `UPDATES.md` 追加 `block` 条目，`oo context check` 返回 20；引擎不可达返回 40（D55）。
    - 任务组：同组两个 Share 版本相同，整组刷新全有或全无（D56）。
    - 完整性约束：同一项目出现两个当前负责人时，该实体不发布、进 `constraint_conflict`，包里写“冲突未决”（D57）。
    - 用户纠错：在实体详情里标记错误后，新版本发布，受影响 Share 出现更新（D59）。
12. 演示 T2 场景 P21（两个并行 Agent，一个用到的决定被推翻后提交被拦住）。

**不在本闭环**：Suggest、OCR、漂移差异摘要、类型升格、MCP 更新订阅（L5）。

**M1 结束 = 第一版可内测。** L4 签收后，发布构建打开 `oo` 的 `docs` feature 并标为实验功能（D41，npm 发布由 owner 操作）。 交付第一个 owner 验收包（60 分册 §3.4、§4），owner 在打包好的 App 上直接体验。flag 仍默认关，但可以对种子用户打开。

### L5 Suggest 回流（M2，S7 + S8，2 周）

**目标**：Agent 学到的东西有路回来，而且人审得过来。

**S7 开始前**：走一次 spec 重新定基线流程，把 MCP `suggest` 工具写进 `docs/08`（D42）。

**S7 —— 写回通道与规则**
- 一致性（D55、D56）：MCP 资源 `puppyone://share/<sid>/updates` 订阅通知与 `context_check` 工具；接受建议前列出用到相关事实的其他进行中 Share，接受后向它们广播更新（B-S7-07）。
- 后端：`suggest/` 目录约定与 schema；MCP `suggest` 工具；`puppyone sync`/`oo context collect` 收集建议；影响式规则（新事实且来源可信 → 自动接受进当日摘要；取代从未被 Brief 用过的事实 → 静默取代；取代已被 Share 用过的事实 → 推人确认并列出受影响任务；改偏好或类型结构 → 一律人工）；“哪个 Brief 用了哪条事实”的使用记录；`editor` 角色。
- 前端：待确认队列新增 `suggestion` 种类；按天合并的摘要视图。

**S8 —— 修订模式审核**
- 后端：建议 → 文件级 diff 的生成；接受后写入 overlay 或回写到 Drive 文件（仅 `editor`，并经 Puppyone 的 Git 自动提交，OO 依旧不直接写 Drive——由 Desktop 执行写入）。
- 前端：修订模式视图（删除线、高亮、按建议或按来源接受/拒绝），参考 track-changes 交互；“影响哪些正在进行的任务”提示。

**验收**
1. 理念文档第 4 节六步完整跑通，第 5 步“点接受”≤ 2 秒。
2. 四类影响式规则各有用例，行为与 D 规则一致。
3. 审核负荷：50 条建议的典型一天，人工操作 ≤ 5 次。
4. 每次接受都在 Git 历史或 overlay 中可追溯到建议、Agent 凭证和证据。

### L6 多模态与演进（M2，S9 + S10 + S10b，3 周）

**目标**：扫描件、图片、录音、录屏都能被读懂并带精确出处进入本体；Drive 和本体会变，Share 跟得上，系统会成长。全部组件符合 [90 分册](90-commercial-boundary.md) 的商用边界。

**S9 —— OCR、图片与类型升格**
- 后端：IR v1.1 契约（B-S9-03）；PaddleOCR sidecar（扫描 PDF、独立图片）；Docling 显式 RapidOCR 与内嵌图片 OCR、坐标换算（B-S9-04）；开放候选统计与 `type_promotion` 提议，升格写入 overlay 后改为受约束抽取。
- 前端：OCR 与图片文字在详情栏的呈现（含低置信区域标记）；类型升格的审核卡片。

**S10 —— 音频与比测**
- 后端：`media-parser` 骨架、自编 LGPL FFmpeg 与解码路径（B-S10-05）；**第一项工作是 ASR 与说话人分离比测并给出选型报告**（B-S10-06）；长音频流水线（B-S10-07）；说话人身份三层与 `speaker_identity`（B-S10-08）；媒体并发池与上限（B-S10-10）。
- 前端：macOS 宿主机解码 helper（F-S10-05）；音视频进度与转写呈现、时间戳跳转播放（F-S10-07）；说话人确认（F-S10-06）。

**S10b —— 视频与演进收尾**
- 后端：视频切镜、关键帧去重、帧 OCR、时间轴合并（B-S10-09）；`refresh` 生成“自上次以来的变化”的差异摘要（轻量漂移已在 L4 完成，D50）；解析器或 prompt 升级 → `outdated` → 后台重跑 → diff 门禁；`puppyone share` 薄封装（puppyone-cloud 的 CLI，调用 OO）。
- 前端：关键帧条带与帧文字；刷新与差异预览；“可更新”文件的批量处理入口；T1/T2 媒体与漂移场景。

**验收**
1. 评测集的扫描件子集，OCR 后核心类型召回率 ≥ 0.65；文档内嵌图表、截图中的文字字符级召回 ≥ 0.9。
2. ASR 与说话人分离比测报告已签收，选型结论与许可判定写入 `supply-chain/` 审计记录。
3. 2 小时合成中文会议（3 人）：核心类型召回 ≥ 0.6；说话人身份确认后，事实主语正确；中途杀掉 `media-parser` 后续跑，不重做已完成的块；同一 ISA 指纹下逐字节可重放；说话人特征文件在处理完成后不存在。
4. 合成录屏视频：每页幻灯片恰好一个关键帧；帧文字召回 ≥ 0.9；`#t=` 出处在 Desktop 中能跳转播放。
5. macOS 上 H.264/AAC 的 mp4、m4a 经宿主机解码处理成功；容器内 FFmpeg 的 `-buildconf` 不含 gpl、nonfree 与被禁解码器；没有宿主机解码器且未配置外部 FFmpeg 时，文件显示 `DOCS_PARSE_CODEC_UNAVAILABLE`。
6. SBOM 许可门禁对 `ocr-parser`、`media-parser` 镜像全绿；`THIRD_PARTY_NOTICES/` 包含全部新组件。
7. 修改一个被 Share 引用的决定，刷新后 BRIEF 头部列出差异。
8. 升级解析器版本：重跑期间已发布事实保持可用，完成后差异进入门禁，无整库抖动。
9. `puppyone share` 与 `oo context mount` 产物一致。
10. 媒体作业运行时，文档处理的单文件延迟仍满足 D49。

## 5. 角色与并行

- OO 主线程独占：根 `Cargo.toml`/`Cargo.lock`、migrations、共享 trait（`DocumentSource`、IR 类型）、`execution/`、合并与发布。
- 后端执行者按 `B-S<n>-*` 卡并行；前端执行者按 `F-S<n>-*` 卡并行；同一时刻两个 writer 不碰同一组文件。
- 原生子智能体同时不超过 2 个；Codex 执行者可多个并行，派发用 `dispatch-retry.sh`。
- 每个闭环签收时，主线程汇报三件事：现在是什么状态、还有什么没做或没验证、下一步做什么。没有实测的东西不写“通过”。

### 7.2 OO 侧验收的口径

- §3 中每个闭环验收项里“在 Desktop 里……”“界面上……”的部分，在阶段一用等价的 OO 呈现形态验证：`oo` CLI（同一控制 API 的命令行）、MCP 工具或资源、控制 API 契约测试；数字口径与原验收项相同。例如 L2 验收 4“Desktop 自动重连并补齐事件”在阶段一验证为“守护进程重启后 `since` 补齐无缺口”，Desktop 的界面重连在阶段二验证。
- 因此阶段一需要让 CLI 覆盖 Desktop 的全部操作面（Drive 登记与同步、文件与状态、待确认队列、实体与纠错、Share 与一致性），这些命令是同一控制 API 的薄客户端，计入阶段一。
- 30 §4 的横切门禁按“OO 侧可执行”的部分在阶段一生效；Puppyone 侧门禁（`check:boundaries`、T1/T2、交付文件 sha256）在阶段二生效，届时对每个已签收闭环补测。
- owner 验收包：阶段一在 L4、L6 结束时交付 **CLI 验收包**（`oo` 二进制、引擎与解析镜像、操作手册与评测集示例，按 60 §4 模板改写为命令行步骤）；打包 App 的 owner 验收包在阶段二按原节奏（对应 L4、L6、L8）交付。
