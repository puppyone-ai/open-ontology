# v0.3 建联能力升级：对照代码的分析与分轮方案

状态：分析与建议，未实现。依据 `specs/relationship-discovery-convergence-plan.md`（2026-11-10 研究稿），对照 `v0.3/integrate`（3fcf0be89）实读代码。

## 1. 结论

1. 现在的建联（`tools/pg-builder/scripts/adjudication.py` + `library_selfbuild.database_containment`）方向是对的：全量、只读、精确聚合，并把证据绑定到摘要哈希。问题在于“认可什么”和“证据传到哪里”。
2. 本轮（v0.3）只做一个小的 **R0 安全补丁**。目标不是发现更多关系，而是保证已发布的关系不会算错，并把证据带进 Pack。约 1 天，不改协议版本。
3. 方案文档里的 R1–R4（候选键注册、名称映射、语义与粒度、Pack 查询导航、持续发布）整体放到下一轮。它们要改 facts、审核和 OOS 协议，不适合在本轮收尾时加。

## 2. 现状与缺口（逐条对照代码）

| # | 现状（代码位置） | 问题 | 后果 | 归属 |
|---|---|---|---|---|
| 1 | `relation_decision`：`supported = 包含度 ≥ 0.9 且 (命名相似 或 JOIN 共现)`，不检查 `parent_unique` | 父键不唯一的关系照样 `adopted`（已实测：containment 0.95、parent_unique=False、命名命中 → `adopted`）；编译成 `many_to_many`，`join_hint: left` | Agent 按这条边 JOIN 会把行数放大，SUM 结果偏大。正对方案 §7“父键重复不发布 many-to-one”这条负例 | **R0** |
| 2 | 实体键回退：没有主键时，取**字母序第一个**满足 `distinct == rows` 的列（`collect` 中 `key = next(...)`） | 金额、时间戳、备注碰巧唯一就会被当成实体键 | 实体身份错，后续关系挂在假键上。方案 §4.1 明确禁止 | **R0** |
| 3 | 证据只算行覆盖率：`containment = matched_rows / non_null_rows` | `database_containment` 已经返回不同值计数（`non_null`、`matched`），但没算不同值覆盖率；也没记录未匹配行数 | 高频值掩盖长尾缺失（方案 §4.3） | **R0**（数据已有，只是没用） |
| 4 | `compile_confirmed_community`（`crates/oo-builder/src/adjudication.rs`）发布关系时**不写 `evidence`** | OOS `RelationEvidence` 已有 `containment / type_compatible / seen_in_query_log` 字段，却一直是空的 | Pack 里看不到覆盖率和依据，Agent 无从判断能不能用（方案 §4.5） | **R0**（现有 schema 内即可补） |
| 5 | 候选召回 `discover_candidates`：两两表 × 两两列，名称正则 `id$|code$|_dm$|_bh$…` | 字段名不同、名称映射（如 `region_name → regions.name`）、非主键唯一键都召回不到；复合键要求同名；全量笛卡尔积，表多时撞 `relationship_check_budget` | 无外键库的建联能力上不去 | R1 |
| 6 | 预算耗尽 `relationship_check_budget_exhausted` 直接抛异常 | 整个裁决失败，不能标记 incomplete 后续接着做 | 大库不可用（方案 §7“预算耗尽可恢复”） | R1 |
| 7 | NULL 排除了，空串和规范化碰撞没有统计 | `''` 能匹配父表的 `''`；`::text` 比较可能吃掉前导零差异 | 错误匹配 | R1 |
| 8 | 同一对表的多条边只靠 edge id 区分，关系名是 `r-<hash>` | 没有角色（发货仓 / 收货仓） | Pack 无法说清该走哪条路径 | R2 |
| 9 | 没有粒度、作用域、快照或有效期的概念 | 目标表与明细表会直接 JOIN | 伪达成率（方案 §4.5） | R2 |
| 10 | `join_hint` 恒为 `left`，Pack 只有关系清单 | 没有“问题 → 路径 → SQL 示例”的导航 | 新会话拿到 Pack 仍不知道怎么查 | R3 |
| 11 | data-only 复用只看 schema（`library_semantics.py`） | 键质量或覆盖率变了，旧证明不会失效 | 新数据配旧关系，仍显示为已认证 | R4 |

## 3. 本轮 R0：四处小改，保证“发布的都是对的”

全部在现有协议内完成：`oo.adjudication/v1`、OOS `RelationEvidence`、阈值文件都不升版本。

1. **父键必须唯一才可采纳**（`adjudication.py::relation_decision`）
   - `supported` 也要求 `parent_unique`；不唯一时规则为 `relation.parent_not_unique`，决策 `rejected`（构建器只接受 adopted/rejected，不加新状态）。
   - TUI 的 `missing_evidence` 已经能显示“父键不唯一”，无需改界面。
   - 测试：补 `({'containment':.95,'name_similarity':1,'parent_unique':False}, 'rejected')`。
2. **实体键回退加类型和名称门槛**（`collect`）
   - 只在文本或整数列中找候选，并且名称像键（复用 `keylike`），或者是全表唯一的那一个候选。
   - 不考虑 numeric 带小数位、浮点、时间、布尔类型。找不到就不设键（`rejected`，规则 `entity_key.no_candidate`），不硬凑。
   - 测试：只有金额和时间戳唯一的表 → 无键。
3. **补不同值覆盖率与未匹配数**（`collect` 的 evidence）
   - 新增 `distinct_containment = matched / non_null`（数据已在 `observed` 里）和 `unmatched_rows = non_null_rows − matched_rows`。
   - 判定先不改（避免阈值漂移），只展示出来。TUI 决策行的证据条加一段“不同值 0.83”。
4. **证据进 OOS 与 Pack**（`oo-builder/src/adjudication.rs::compile_confirmed_community`）
   - 写入 `evidence: {containment, type_compatible, seen_in_query_log: join_cooccurrence}`。
   - 多对多一律不发布（与第 1 条互为兜底）。
   - 测试：编译出的 relationships 带 evidence，且 OOS 校验通过。

注意：第 3 条改了 evidence 内容，`summary_sha256` 会变。demo 与 CLI 共享的 `deploy/lite/demo/adjudication.json`、`crates/oo-cli/tests/fixtures/adjudication.json` 需要按 d526f8bf4 的流程一起重算。这是本轮唯一的跨 lane 影响点。

验收：`python3 -m unittest test_adjudication`，加上 `cargo test -p oo-builder -p oo-cli`；用真实 PG 跑一次 demo 裁决，前后对比确认已采纳关系里没有 `many_to_many`。

## 4. 下一轮：R1–R4 的落地拆法

按方案文档的顺序，每个闭环一条可独立验收的分支，并给出起手位置。

### R1 候选键与确定性关系（无外键也能连）

- 新模块 `tools/pg-builder/scripts/candidate_keys.py`：注册声明主键/唯一键、观察唯一键（绑定 facts 摘要）、复合候选键。分别统计 NULL、空串、规范化碰撞（trim / lower 后 distinct 数变化）。数值型、时间型、金额型不进候选。
- 召回改为“分组 + 父键缓存”：按类型族和值形态（长度分布、前导零、字符集）分桶，只在桶内配对；父键统计缓存一次。名称映射第一版只支持快照内精确匹配（child 文本列 → 父表唯一文本列）。
- 预算耗尽改为 `incomplete` 并写 checkpoint，`oo build --resume` 可续跑。
- `database_containment` 增加子键最大父行数（膨胀证据）、空串排除，以及规范化后碰撞计数。
- 验收：合成库（无外键、字段名不同）自动发现多个角色关联；重复父键、空表、同名异义、唯一金额等负例被拦截；真实 PG 上 JOIN 前后行数不变。

### R2 语义、角色与粒度（大区 / 组织 / 目标能一起查且不算错）

- 关系类型扩展：声明引用 / 推断 ID / 快照名称映射 / 审核别名 / 作用域-时间关联 / 聚合后指标关联。
- 角色命名：同一对表多条边时由模型提议角色名，SQL 验证后才进入审核；无语境时两条都展示，不默认合并。
- 数据集粒度：每张表登记行粒度；目标类表标注期间、组织、版本、单位。缺任一项时只允许查原值，不允许算达成率。
- 协议：`oo.adjudication/v2`（加 role / kind / grain / scope），OOS 显式版本化扩展，审核 TUI 在决策页展示角色与粒度。
- 模型只能选目录里存在的列，允许弃答；失败时保留确定性结果，标 incomplete。

### R3 YAML 与 Pack 的“怎么查”

- `role_pack.rs` 产出查询导航：起点表、粒度、角色、JOIN 键与类型、覆盖率、未匹配处理、可用维度、聚合规则、禁用原因。
- 每条路径带一个经过 dry-run 校验的 SQL 示例；目标与实绩先各自聚合到同粒度再关联。
- 验收：新会话只拿导出的 Pack 和认证入口，就能回答一个跨三表的联合问题，并能追溯 SQL。

### R4 持续更新与发布

- data-only 失效：键唯一性、覆盖率、别名或重复数变化时，相邻关系重新验证；旧证明失效后保留上一完整发布版本，新关系标为未认证。
- 文件 sealed import 的合法发布适配，并接入统一完成事件；数据库 CDC 的 checkpoint 保持独立。
- 验收：第二次导入、内容重叠、键变化、失败重试、重启和回滚全部通过；发布失败时 Gateway 仍服务上一版。

## 5. 与 v0.3 其他工作的关系

- 屏 1 已改为“选择优先 + 实时检查”（3fcf0be89）。数据库与表的服务端发现由独立会话在做（PG/Oracle 连接器 `discover_tables` 与数据库列表）。那是 R1 召回的前提：表清单来自服务器，而不是 `--catalog`。
- 审核屏（屏 4）已经能展示证据条与“改判”。R0 补上的不同值覆盖率与 evidence 字段能直接显示；R2 的角色与粒度需要在决策页加两列，属于下一轮。
