# ADR-031 以业务可回答性和角色可执行闭包约束语义交付

> Status: Proposed（本次设计修订采用的目标；实现与验收待完成）
> Date: 2026-10-21
> Owner: Open Ontology Engineering / 业务指标 owner
> 部分替代：ADR-005 的自由 SQL 效用推论与指标推迟策略、ADR-012 的“唯一改写”说明、ADR-013 的默认可 JOIN 假设。不替代其文件语义、列级授权和受控派生资产原则。

## 背景

当前交付的结构与描述资产并未闭合 grain、码义、指标及示例的审核投影。
Pack 可能丢失公共类型，或指向未在当前角色发布的字典对象。
Gateway 使用 PostgreSQL 解析器，但只实现有版本的安全子集。
技术题通过、SQL 执行成功和发布 live 均不足以证明“全部实收”等业务问题可回答。

证据、代码落点和实施范围见[全链路整改方案](../../../docs/semantic-query-chain-remediation-plan.md)。

## 决策

1. 首个交付单元为指定指标、角色、期间/范围的可回答业务切片。观测、语义、分类、授权、执行、源覆盖/时效和业务验收分别记录，不引入可被误读为全部就绪的单一标记。
2. 保留 OOS YAML 唯一语义源和少量正交接口。关键指标现在就需要已审核、可执行、可对账的 recipe 或受控场景资产；通用指标编译器仍可延期，不把财务建模推给每次 Agent 问答。
3. 公开 SQL 能力按当前函数/运算符签名、AST 形状和预算声明；缺失能力必须准确报告。只允许经过测试的星号展开、逻辑物理绑定及支持的别名/排序重写，不修改业务筛选条件以换取成功。
4. 角色 Pack 的所有执行指引必须形成真实引用闭包。oo_dict/oo_entity 等必须先安装、授权并通过当前 Gateway 验证；否则只说明缺口，或使用另行审核验证的 recipe，不生成不可执行指令。
5. 公共标准类型、真实对象引用和自由文本分别处理，类型保真不以放弃保密为代价。未知状态不得静默排除后继续认证完整金额；只允许明确限定的小计。
6. 技术发布和业务认证分开；完整性、安全、关键正确性门禁不可强制跳过。回滚需验证数据/派生资产/策略/Pack 兼容，不恢复撤销权限。

## 不变与非目标

- 保留单向只读边界、列权限/RLS、OID 校验、成本控制、审计以及 ADR-029/030 的单库单 Pack 和原子发布原则。
- 不新增任意 SQL 通道，不授予更大角色，不提供 Agent 直连源库后门。
- 不要求立即交付通用指标 DSL、向量库、全库实体消解或增加模型阶段。
- 本 ADR 不直接增加 OOS 字段/API；正式契约变化必须同步 schema、兼容迁移和测试。

## 后果与验收

需要补齐候选到审核到 effective 的覆盖账本、当前能力诊断、角色 Pack 执行闭包及业务对账。
未通过的指标保持未就绪，无关且口径明确的授权计数仍可用。

验收按整改方案 A01–A26 逐项留证；首批关键题在外部真实 CLI/模型冷会话独立运行三次，
与预先冻结的独立 oracle 对照。旧技术题保留回归但不替代业务题。
未满足时不得把本 ADR 标为 Implemented，也不得宣称业务交付完成。
