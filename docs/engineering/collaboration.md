# 协作方式

> Last reviewed: 2026-11-16

## 1. 角色

| 角色 | 负责 | 不做 |
|---|---|---|
| 协调者（主线程） | 定范围与契约；写并冻结任务卡；派发、签收；写所有共享文件；合并、发版；向 owner 汇报 | 把集成和共享文件交给执行者；不经核实就把执行者的报告当结论 |
| 执行者（长程任务） | 领一张冻结的任务卡，在独占的 worktree 和写域内端到端完成，并交付固定证据 | 派生自己的执行者；改写域外文件；push、开 PR、发版（任务卡另有授权的除外） |
| 判断型子任务 | 根因定位、CI 收敛、视觉设计、性能测量这类需要判断力的工作 | 同一时间超过约定的并发上限 |
| owner | 决定范围和取舍；发布 npm；公开镜像；管理账号与凭证 | — |

**共享文件只有一个 writer**，由协调者负责：根 `Cargo.toml` 与 `Cargo.lock`、`migrations/`、共享 trait 公共接口、`supply-chain/`、`execution/` 台账、`ci/gates.yaml`、生成文档。执行者需要改这些文件时，把精确补丁写进报告，由协调者合入。

## 2. 任务卡

任务卡放在 `execution/v0.x/cards/`，通用规则在同目录的 `_common.md`。一张卡至少写清楚：

- 对应的 Plan 条目与 trailer（`Plan: <任务号>`）；
- 分支、基线 SHA 和 worktree；
- 写域（可以改的目录），以及明确不能改的目录；
- 输入、契约，以及上游产物的固定 SHA；
- 资源上限：容器标签、同时运行的数据库容器数、内存、磁盘底线；
- 退出条件：要跑哪些测试，什么样的结果算通过；
- 报告格式：提交列表、测试结果、证据路径、需要协调者合入的补丁、遗留问题。

接口或范围要变，先改卡再改代码。续作卡开头写清楚三件事：已经确认的事实、已有的提交、"不要重做已提交的部分"。

## 3. 派发与续跑

- 每个执行者用一个独立的 git worktree，不能两个执行者共用。
- 派发脚本：`execution/v0.x/dispatch.sh <卡片> <worktree>`，一定要用外层的 `dispatch-retry.sh`。模型服务返回 502 或用量超限（429）时，它会等待后自动续跑，每次续跑生成一张 `-rN` 续作卡。这些 `-rN` 卡是运行产物，不要提交。
- 派出去之后靠完成通知唤醒，不要短间隔轮询。长时间运行（构建、全量回归、T10）一律放到后台。
- 执行者停止后，要检查它是否留下了在后台运行的进程或容器。

## 4. 签收

执行者的报告只是线索，不是结论。签收时要做到：

1. 读报告和提交列表，到证据文件或 CI 里核对关键数字；
2. 报告里写 `partial` 或 `not done` 时，判断卡住的地方是真的外部阻塞，还是执行者自己停下了。后者直接派续作卡，并在卡里写明"不要提前停"；
3. 外部阻塞（额度、资源）不是放弃的理由：换执行者，或者调整资源后重派；
4. 没有实测的项目，不能写成"通过"；估算要标明是估算。

## 5. 台账

| 文件 | 规则 |
|---|---|
| `execution/v0.x/state.json` | 当前状态的唯一来源，直接覆盖写 |
| `execution/v0.x/ledger.md` | 只追加。行号（E 编号）连续，更正也写成新的一行 |
| `execution/v0.x/decisions.md` | 只追加，记录 owner 的指令和范围变化 |
| `execution/v0.x/TODO.md` | 由 `render_todo.py` 生成，不手改 |

改完台账之后跑一遍：`python3 execution/v0.2/render_todo.py --check`、`python3 specs/scripts/check_spec.py`、`check_plan.py`、`check_v02_plan.py`。

## 6. 提交、合并与公开信息

- **提交身份**：只用 owner 的身份。不加 `Co-Authored-By`，也不加任何 agent 署名；trailer 只写 `Plan: <任务号>`。
- **合并条件**：PR 上**所有**检查都通过，包括 `aggregate` 和 `oo-test-fast-l1-l2`，才能做普通 merge。不能 force push。不能为了变绿放宽策略、门禁或测试。"之前就是红的"不能作为合并理由，必须先修到绿。
- **公开仓库卫生**：
  - 提交前用私有词表做一次 `grep -i -f` 检查，结果必须为 0；
  - 不写客户名称和内部主机名；
  - 不写模型 endpoint、key 或任何凭证。凭证只能通过 `secret_ref` 按路径引用；
  - 证据里不能出现无关容器的名称，也不能保留 docker 清单。
- **`docs/*.md` 与 `docs/product/*.md` 受 spec 基线哈希锁定**，改动要走 spec 流程（更新 `specs/sources-baseline.json`，并在 spec 中引用）。子目录（`docs/guide/`、`docs/reference/`、`docs/engineering/`）不受此限制。

## 7. 主机与容器

- 我们自己创建的容器都要打 `oo.lane=<lane>` 标签，用完删掉。
- 主机上的其他容器不要停、不要改、不要 inspect，也不要把名称写进任何文件。需要判断主机是否繁忙，只用 `docker stats` 读 CPU。
- 资源约束见 [testing.md §5](testing.md#5-主机资源约束)。

## 8. 汇报

向 owner 汇报时只写三件事：

1. 现在是什么状态；
2. 还有什么没做或没验证；
3. 下一步做什么。

结论放在最前面。遇到需要 owner 拍板的取舍，给出推荐选项。用 owner 指定的语言。
