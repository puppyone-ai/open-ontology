# FM11 review: integrity constraints (`formal/quint/constraints.qnt`)

Model of D57 (10 section 16.7): the four core constraints over time slices, partial blocking, no violating fact current in any pack. Code:
`publish/constraints.rs`, `temporal.rs` (`plan_group`), `review/decide.rs` (`constraint_conflict`), `share/drift.rs` and
`compile/*` (conflict lines). Spec: 80 section 3.1 (FM11). Card V-S6-03.

Review status: author self-review done (lane A, 2026-11-17); independent review (board lead plus a native sub-agent) **not yet done**.

## 1. Model shape

- One functional-dependency shape covers the four constraints: kind 0 `project_single_owner` (key = project, value = owner), kind 1
  `decision_single_status`, kind 2 `identity_unique_person` (not time dependent), kind 3 `rejected_not_adopted` (value 0 = rejects, 1 = decides).
  Two facts of one (kind, key) with different values conflict when their intervals overlap (kind 2: always). 4 time slices, `hi = 4` open.
- A publish run takes the incoming facts (drafts and still-held ones) in the order of the temporal pass (start slice, then id: a published fact
  is always met first, higher confidence wins an equal start), each against what is published so far. A conflict is held (stays out of the
  version, an open violation for the (kind, key)); everything else publishes (partial blocking). A rule-certain, later-starting value (kinds 0
  and 1) ends the earlier one at its own start whichever arrives first (D51: not a violation). A person resolves a violation by naming the
  winner (overlay, publishes in the next run); the facts it conflicts with are retracted or rejected and become `ban` (the same content is
  rejected on arrival, DOC-G4). Held facts that no longer conflict wait for the next run.
- Bounds: 6 facts, 2 keys per kind, 3 values, 4 slices; actions: add a draft, publish, retract (source deleted), resolve, compile a pack.

## 3. What the model found (patched)

1. `rejected_not_adopted` compared incoming facts against **published** facts only: a `rejects` and a `decides` of one alternative arriving in the same
   run both published. Fix: the check also meets incoming facts of the run (by confidence, then fact key) and blocks the lower one; a fact is not blocked by
   one that is itself blocked (greedy).
2. A pending `supersede_candidate` item was retired by `enqueue` while the temporal pass still held its fact, and `queue_held` could not re-queue it
   (dedupe): a held fact waited for nobody (same fix as FM5 finding 4).

## 4. Readings and limits (no patch)

1. Kind 3 has no certain supersession in the code (a later `decides` over an earlier `rejects` is always a violation for a person); the model follows it.
2. The temporal pass settles an **equal start** before it asks whether the winner can publish: an uncertain value with higher confidence blocks a rule-certain
   one that started the same day, and itself waits as a candidate. Safe, not minimal: 4 of 300 replayed traces end at such a state (valid, different from the model).
3. The violation and its `constraint_conflict` item name the first conflicting **pair** only. With three or more values of one key, resolving takes several
   rounds, and the engine settles the two facts named: a third published value stays. The replay counts the traces where the model resolves a fact the item does not
   name (28 of 300) and ends them there.
4. `identity_unique_person` concerns Person entities (the merge fails, nothing is held): the model keeps kind 2 as facts; the replay profile leaves it out
   (`constraints_live.rs`, `resolve_live.rs`).

## 6. Conformance

`conformance_constraints.rs`: a trace step is run on the real publisher, states compared; where the engine takes another valid outcome the safety oracle
(no two current values by slice, held facts wait, unrelated facts publish) still runs and the trace ends. Counts in the L4 report.

## Independent review (native sub-agent, 2026-11-17, commit e82490f57)

Verdict: APPROVE WITH CHANGES. Reviewed: `constraints.qnt` against 10 16.7, D57 and D51, `publish/constraints.rs` (by the model's own description of the greedy check), and `tests/conformance_constraints.rs` / `constraints_live.rs` (profile `stepLive`). Checks: `quint typecheck` passes; `quint run` (seed 7, 30 steps) finds no violation on the unmodified model. The invariant set restates the no-overlap rule per time slice (`invNoCurrentViolation`) without calling `conflict`, which is the right independence.

Mutation checks (copies in /tmp, `--invariant=inv`, 3000 samples, seed 7):
- C1, no conflict detected in the greedy pass (`bad` always empty): violation (caught).
- C2, `supersedes` without the rule-certain flag (an uncertain value ends an older one): violation (caught by `invCertainNotViolation`).
- C3, the DOC-G4 ban is never set on resolve (`ban: false`): **no violation**. Blocking, see B1.

Blocking
1. **B1, DOC-G4 (a person's rejection holds on re-arrival) has no invariant.** The `ban` flag is set in `resolve` and checked in `publishRun`, but the mutant that never sets it passes `inv`. I tried the obvious invariant ("no published fact has the content of a banned fact") on the unmodified model and it is violated, but the trace is not yet explained: the likely cause is that a person may assert the same content later (`resolve` on a new slot makes it `draft` and does not clear the ban on the old one), which is legitimate. The author must (a) state precisely what the ban forbids: a publish run (not a person's overlay) may never publish content whose banned twin is still in the history, and (b) add that as an invariant that is independent of `publishRun`. Until then DOC-G4 is not checked by the model.

Non-blocking
2. The live replay (`stepLive`) covers kinds 0, 1 and 3 only. Kind 2 (identity constraint, D74) is covered by `constraints_live.rs` and the resolver tests, not by the trace replay. The `invNoCurrentViolation` kind-2 branch (value count over the whole history) is therefore model-only. Note this in FM11.md, or add kind 2 to the replay profile.
3. `publishRun` picks candidates by rank with `fold(-1, ...)` over same-rank ids. Keys are unique (`lo*100 + i`), so ranks are unique and the pick is deterministic; but the ordering is a model choice (the spec says "confidence, then created order"). The model's comment says the id order stands for "any order": make the choice explicit in the invariant list, because a different tie-break in code is not a counterexample to the model but it is a difference from the spec.
4. `invWellFormed` uses `hi <= TMAX`; a backfilled older value that is cut (`hi: cut`) can have `lo == hi`? `cut` is the start of a newer certain value which is at least `f.lo + 1` (supersedes requires `a.lo < d.lo`), so `lo < hi` holds. Keep it; say so in the header if the rule changes.
5. Bounds: 6 fact slots, 2 keys, 3 values, 4 slices. Witnesses are reachable (`quint run` witnesses not re-checked here); the rule-certain supersession with equal start (the "equal starts are a conflict" clause in the header) has no witness. Add `witEqualStartConflict`.

Checked and fine: kind 2 ignores time (`conflict` uses `a.kind == 2 or overlap`); kind 3 (rejects/decides) is never superseded (`supersedes` requires kind 0 or 1), matching the header; `resolve` retracts published conflicting facts and rejects waiting ones, and the winner is re-drafted for the next run (no direct publish).
