# FM10 review: freshness token and coverage (`formal/quint/freshness_token.qnt`)

Model of D54 (10 section 16.2): `drive.rev`, `covers_drive_rev`, `min_drive_rev` / `wait_ms` / `require_complete` and the
`coverage` structure. Code: `store/rev.rs`, `publish/run.rs`, `share/coverage.rs`, `compile/coverage.rs`, migration 0142 (triggers).
Spec: 80 section 3.1 (FM10). Card V-S6-03.

Review status: author self-review done (lane A, 2026-11-17); the independent review by the board lead plus a native sub-agent is **not yet done**.

## 1. Model shape

- Changes 1..6 of one Drive: a file version (`pending` -> `ready` -> `ok`, or `pending` -> `fail`) or a correction (`ready` until a publish
  consumes it). 3 files. `upload` takes the next rev and ends an older unfinished change of the same file as superseded (terminal).
- A publish run is `beginPublish` (the batch = what is ready now) and `commitPublish` (the batch becomes `ok`, `covers` = largest terminal
  prefix at commit time, never lower than before) or `abortPublish`.
- `compile(min_drive_rev, scope, require_complete, wait elapsed)`: covered -> compile now; not covered -> only after the wait. The compile
  measures coverage live (largest terminal prefix now) and lists in-scope files whose latest change is pending or failed.

## 2. Rule to model to code

| Rule | Code | Model | Invariant |
|---|---|---|---|
| `drive_rev` advances for every change and is gap free | triggers `file_version_rev`, `file_state_rev`; `bump_drive_rev` for corrections | `upload`, `correct` | `invRevGapFree` |
| `covers_drive_rev` only advances when all changes <= r are terminal, never goes down | `store::rev::covers_drive_rev`, `publish/run.rs` | `commitPublish`, `prefixTerminal` | `invCoversSound`, `invCoversMonotone`, `invCoversMax` |
| a compile does not run ahead of the live truth | `share::coverage::measure` (live measure) | `compile` (`live`) | `invLiveCoversSound` |
| wait, then compile with an honest coverage | `coverage::prepare` | `compile` | `invCompileWaits` |
| `require_complete`: only a Drive covered to the current rev with nothing pending or failed in scope | `Coverage::complete` | `complete` | `invRequireComplete` |
| `pending` and `failed` are exactly the in-scope files not covered; counts add up | `measure` | `exist`, `pend`, `fld` | `invCoverageHonest`, `invCoverageInScope` |
| a correction takes a `drive_rev` and is not covered before a version holds it | `routes_correct.rs` | `correct` (`ready`) | `invOverlayAdvances` |

## 3. What the model found (patched)

- **Corrections were never pending.** `covers_drive_rev` (stored and live) was the smallest pending file version minus one, or `drive.rev`:
  an overlay that took a `drive_rev` but was not in any version yet counted as covered. A task started right after a correction
  (`min_drive_rev` = the rev the correction returned) compiled at once, without the correction, and `coverage` said complete. Fix:
  `store/rev.rs` treats an overlay written after the last version (live) or after the start of the publish transaction (stored) as pending
  (`covers_drive_rev_live`). Residual race, not closed: a correction committed during a publish run that started before it is counted
  consumed by the stored number; the model forbids that interleaving in the replayed profile (`stepLive`, `correct` only when no run is in flight).

## 4. Readings of the spec

1. `require_complete` in the code is stricter than "covered up to `min_drive_rev`": it also fails when a file of the scope failed
   (`failed` non-empty) or when the Drive has changes after `min_drive_rev` not yet covered. The model follows the code (the stricter
   reading cannot hide a missing file).
2. The stored `ontology_version.covers_drive_rev` is a lower bound: a file with nothing left to publish is promoted to `published` after
   the run (and a run that makes no version stores nothing); the compile uses the live number. The conformance test checks
   "stored never ahead" and "live equal to the model".
3. `covers_drive_rev` is one number per version over all Drives (the smallest); the model has one Drive.

## 5. Mutation checks

| # | Mutation | Caught by |
|---|---|---|
| M1 | covers = highest finished change, not the terminal prefix | `invCoversSound`, `invLiveCoversSound` |
| M2 | coverage lists pending files outside the scope | `invCoverageInScope`, `invCoverageHonest` |
| M3 | `require_complete` succeeds with a failed file in scope | `invRequireComplete` |
| M4 | a correction does not take a `drive_rev` | `inv` (`invRevGapFree`, `invOverlayAdvances`) |

## 6. Not modelled

wait duration arithmetic, event subscription latency, several Drives, the `superseded` / `deleted` rev bumps (terminal at creation, they cannot
lower coverage). Liveness (coverage catches up) by witness `witCaughtUp`.

## 7. Conformance

`conformance_freshness.rs`: a database per trace; `drive.rev` equal at every step, live coverage and the 409 equal at every `compile` step, stored
`covers_drive_rev` never ahead.

## Independent review (native sub-agent, 2026-11-17, commit e82490f57)

Verdict: APPROVE WITH CHANGES (no blocking finding; the changes are model-precision notes). Reviewed: `freshness_token.qnt` against 10 16.2 and D54; `store/rev.rs` (`bump_drive_rev`, `covers_drive_rev`), `api/packs.rs` (`min_drive_rev`, `require_complete`), `share/coverage.rs`, and `tests/conformance_freshness.rs` (profile `stepLive`, compares the Drive rev, stored covers, coverage fields and the 409). Checks: `quint typecheck` passes; `quint run` (seed 7, 40 steps) finds no violation on the unmodified model.

Mutation checks (copies in /tmp, `--invariant=inv`, 3000 samples, seed 7); all caught:
- F1, commit writes `covers = rev` instead of the terminal prefix: violation (`invCoversSound`).
- F6, a ready file is not counted as pending in the compile: violation (`invCoverageHonest`).
- F7, the scope is not applied to the listing (`exist` over all files): violation (`invCoverageInScope`).
- F8, `require_complete` never answers 409: violation (`invRequireComplete`).

Non-blocking
1. **N1, superseded changes are encoded as `ok`.** `upload` turns an older pending or ready change of the same file into `ok`, which the model's comment calls "superseded (terminal)". Since `ok` also means published, `witCoverLag` and `invCoversSound` cannot tell a superseded change from a published one. Add a third terminal state `superseded` and make `terminal` accept both; the result is unchanged, but the model then matches the wording of 10 16.2.
2. **N2, `invCompileWaits` is tautological.** `timedOut = not(covered)` and `rec.covered = live`, so `timedOut implies covered < minRev` is always true. It only catches a nondeterministic flag that lies. The wait itself is not modelled (a compile is atomic at one instant), so a change that makes the token covered during the wait is not explored. Say so in the header, or split the compile into "start" and "finish" so the wait is an interleaving.
3. **N3, the timeout path is not conformance-tested.** `conformance_freshness.rs` runs `compile` with no wait (its own comment), so the `tmo` branch of the model is checked only as "the compile was done". Code behaviour for `min_drive_rev` above the current rev (the model guards `mr <= rev`) is not stated; check that `api/packs.rs` returns a 4xx and add it to the model's excluded set.
4. `invRevGapFree` allows `rev` to grow by one per step, but `prevRev` is set by every action, so the check holds even if an action changes `rev` twice. Acceptable for one action per step; note it.
5. The two-Drive minimum (the version holds the minimum over Drives) is not modelled, as the header says; keep it as an open point in FM10.md.

Checked and fine: the coverage counts in `compile` (`processed + pending + failed = inScope`) and the rule that `pending` and `failed` are the in-scope files whose latest change is unfinished or failed, which matches the BRIEF line in the header; `commitPublish` takes only the batch of ready changes (process only moves pending changes, so no batch change can become `fail` in the model).
